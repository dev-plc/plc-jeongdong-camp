# DB 도입 설계 (이번 캠프 **미적용**) — Firebase vs Supabase

> **상태**: 설계·비교만. 이번 정동 캠프에는 넣지 않습니다 (D-017 유지).
> **제품도 아직 고르지 않았습니다** (D-029). 고를 때 볼 것을 근거까지 적어 둡니다.
>
> 🔴 **이 문서에는 가격 수치가 없습니다.** 두 회사의 가격 페이지가 작업 환경의
> 네트워크 정책에 막혀 **확인하지 못했습니다.** 기억으로 채우면 틀린 숫자가
> 문서에 박히고, 그걸 근거로 결정하게 됩니다. 확인 방법만 적습니다.
> (이전 판에 있던 Spark 한도 수치는 검증되지 않은 값이라 **지웠습니다.**)

## 왜 이 문서가 있나

`classfinder.plch.kr` 을 같은 구조(GAS 웹앱 + 구글 시트)로 운영해 본 결과
**응답이 느렸습니다.** 추측이 아니라 운영 경험입니다. 그래서 "시트를 원본으로 두되
가운데에 DB 를 끼우는" 구조를 검토했고, 결론은 **읽기 미러(read mirror)** 입니다.

이번엔 안 넣습니다. 대신 GAS 쪽 왕복 횟수를 실제로 줄였습니다(D-017 표).
아래 [넘어갈 기준](#넘어갈-기준) 수치에 걸리면 그때 이 문서대로 진행하면 됩니다.

## 0. 먼저 — 이 프로젝트의 규모

결정을 하기 전에 크기를 봐야 합니다. **작습니다.**

| 항목 | 값 |
|---|---|
| 명단 | **145명** (마스터 탭 실측) |
| 회차 | 2~3개 (`10/31` · `11/07` · 사전답사) |
| 실사용 | **회차당 하루 몇 시간.** 나머지 날은 사실상 0 |
| 동시 접속 | 최대 ~150. 같은 화면을 반복해 보는 **읽기 위주** |
| 쓰기 | 조장의 지점 체크(조당 4건) + 일지 수십 건 = **하루 수백 건** |
| 사진 | Google Drive (D-010). **옮기지 않습니다** |

**이 규모에서 두 제품 모두 무료 한도를 넘길 이유가 없습니다.**
그래서 **비용은 결정 요인이 아닙니다.** 결정 요인은 **인증**과 **운영 리스크**입니다.

> 그래도 한도는 확인해야 합니다. 확인할 항목만 적어 둡니다 —
> 무료 플랜의 저장 용량 · 일일 읽기/쓰기 · 월 전송량, 그리고 유료 전환 조건.

## 1. 권장 구조 — 읽기 미러, 단방향 (제품과 무관)

```
[쓰기]  앱 ──→ GAS ──→ 구글 시트   (지금과 똑같이. 원장은 시트다)
                        │
                        └─ 변경 감지 ──→ DB   (단방향 복제)

[읽기]  앱 ──────────────→ DB      (빠름. 시트를 거치지 않음)
```

핵심은 **화살표가 한 방향**이라는 것입니다.

### 왜 양방향이 아닌가

양방향으로 만들면 같은 레코드를 시트와 DB 양쪽에서 고칠 수 있게 되고,
그 순간 **충돌 해결 규칙**이 필요해집니다. "누가 이겼는가"를 정하는 로직은
행정팀이 시트를 직접 고치는 이 프로젝트의 운영 방식과 정면으로 충돌합니다.

무엇보다 **"시트가 원장"이라는 전제 자체가 깨집니다.** 그러면 장애 시
"시트만 보면 된다"는 복구 경로(→ `ARCHITECTURE.md`)를 잃습니다.
단방향이면 DB 는 언제든 **버리고 다시 만들 수 있는 캐시**입니다. 이 성질이 중요합니다.

### 동기화 트리거

| 방식 | 지연 | 장점 | 단점 |
|---|---|---|---|
| **GAS 시간 트리거 (1분)** | 최대 1분 | 구현이 가장 단순. 실패해도 다음 회차가 복구 | 1분 지연. 변경이 없어도 계속 도는 낭비 |
| **`onEdit` 단순 트리거** | 즉시 | 사람이 시트를 고친 순간 반영 | **웹앱이 쓴 값에는 안 걸린다**(단순 트리거는 사람 편집만). 실행 시간 제한이 짧다 |
| **쓰기 시점 동시 기록** | 즉시 | 지연 없음. 앱이 쓴 것은 확실히 반영 | 쓰기 경로가 느려짐. DB 실패 시 롤백 문제 |

**권장: 시간 트리거(1분) + 쓰기 시점 동시 기록의 조합.**
앱이 쓴 것(`Progress`·`Journal`)은 쓰는 김에 같이 밀어 넣고,
사람이 시트를 직접 고친 것(`Participants`·`Config`)은 1분 트리거가 주워 갑니다.
`onEdit` 은 웹앱 쓰기를 못 잡으므로 **단독으로는 쓰지 않습니다.**

동기화는 **전량 덮어쓰기(full replace)** 로 시작하는 편이 안전합니다.
이 규모(참가자 145명, 탭 10개)에서 증분 계산의 복잡도가 이득보다 큽니다.

## 2. 🔴 결정 요인 ① — 인증. **여기서 갈립니다**

로그인은 **이름 + 연락처 뒷 4자리**이고, 신원의 근거는 계정이 아니라 **시트 명단**입니다
(D-003). 앱이 DB 를 **직접 읽으려면** 그 DB 가 알아보는 토큰이 필요합니다.

**지금 이 프로젝트가 이미 하고 있는 것** (`gas/Auth.gs`, `issueToken_`/`sign_`):

```js
Utilities.computeHmacSha256Signature(payloadB64, getTokenSecret_())   // HMAC-SHA256
// payload: { pid, exp } · base64url · 비밀은 스크립트 속성의 TOKEN_SECRET
```

| | **Firebase** | **Supabase** |
|---|---|---|
| 앱이 직접 읽으려면 | Security Rules + **Custom Token** | RLS + **JWT** |
| 서명 방식 | **RS256** — 서비스 계정 **개인키** | **HS256** — 프로젝트 JWT secret |
| GAS 에서 | `computeRsaSha256Signature` 로 가능하나 **새로 붙여야 함** | **이미 쓰는 `computeHmacSha256Signature` 그대로** |
| 지금 코드와의 거리 | 개인키 보관 + JWT 조립을 새로 설계 | 헤더 세그먼트와 표준 클레임(`sub`·`role`·`exp`)만 추가 |

**Supabase 쪽이 지금 코드에서 훨씬 가깝습니다.** 토큰 발급을 새로 만드는 게 아니라
**있는 것을 JWT 모양으로 맞추는** 수준입니다.

### 공정하게 — 키 보관 위험은 **양쪽 다** 남습니다

행정팀이 시트에서 스크립트 편집기로 들어갈 수 있어 **스크립트 속성을 볼 수 있습니다.**
다만 성격이 다릅니다.

- **Supabase 의 대칭키**: 유출되면 **누구나 임의의 토큰을 위조**할 수 있습니다.
  같은 키로 검증도 하기 때문입니다.
- **Firebase 의 개인키**: 유출되면 마찬가지로 임의 사용자를 사칭할 수 있습니다.
  다만 검증은 공개키로 하므로 키가 쓰이는 자리는 더 좁습니다.

**둘 다 "스크립트 편집기 접근 = 전체 사칭" 입니다.** 정말 막으려면 서명을 GAS 밖으로
빼야 하고, 그러면 관리 대상이 하나 더 늘어납니다.
**→ 1단계(공개 데이터)에서는 이 논의가 통째로 필요 없습니다** (§4).

## 3. 결정 요인 ② — 데이터 모양

**시트는 표입니다.** 행과 열.

| | **Firebase (Firestore)** | **Supabase (Postgres)** |
|---|---|---|
| 모델 | 문서 / 컬렉션 | **표. 시트와 같은 모양** |
| 시트 → DB | 매핑을 한 번 더 설계해야 함 | `마스터` → 테이블, 헤더 → 컬럼 |
| 조 키 `(참여 일자 + 조 배정)` (D-011) | 합성 문서 ID 를 계속 만들어야 함 (지금 `teamKey_` 가 하는 일이 DB 안으로 들어옴) | **복합 인덱스 하나** |
| 관리자 집계 (회비 합계·조별 진행률) | 클라이언트 집계 또는 별도 카운터 | **SQL 한 줄** |
| 실시간 (BACKLOG B-01) | 됨 | 됨 |
| 행정팀이 직접 들여다보기 | 콘솔에서 문서 단위 | 표 편집기 — **시트와 비슷해 덜 낯섦** |

시트를 원장으로 두는 이 프로젝트에서는 **모양이 같은 쪽이 옮길 것도 설명할 것도 적습니다.**

## 4. 그래서 1단계는 **제품을 안 골라도 됩니다**

**1단계: 공개 데이터 5개 탭만 미러링** — `Config`·`Checkpoints`·`Timeline`·`Notices`·`Courses`.

| 탭 | 미러링 | 이유 |
|---|---|---|
| `Config` | ✅ | 모든 요청이 읽는다. 변경은 드물다 — 캐시 효율 최고 |
| `Checkpoints` | ✅ | 사실상 고정. 읽기만 발생 |
| `Timeline` | ✅ | 고정. 첫 화면에서 바로 필요 |
| `Notices` | ✅ | 자주 읽고 가끔 쓴다 |
| `Courses` / `Teams` | ✅ | 작고 자주 읽는다 |
| `Participants` | ⚠ **개인정보** | 미러링하려면 인증이 먼저다. 연락처는 **절대 올리지 않는다** |
| `Progress` | ⚠ | 실시간성이 필요하면 이득이 크다(B-01). 쓰기 충돌 설계 필요 |
| `Journal` | ⚠ | 승인 상태가 자주 바뀐다. 규칙 설계 필요 |
| `Log` | ❌ | 감사 기록. 앱이 읽지 않는다. 미러링 이득 0 |

**이 다섯에는 개인정보가 0 입니다.** 읽기를 전체 공개로 두면 §2 의 인증 문제가
**통째로 사라집니다.** 첫 화면 로딩이 가장 잦은 요청이므로 이득의 상당 부분을
여기서 가져갑니다.

**→ 제품 선택을 미룰 수 있습니다.** 1단계를 하고 실측한 뒤, 개인정보까지 갈 때 정합니다.

## 5. 🔴 가격보다 먼저 확인할 것 — 운영 리스크

캠프는 **몇 주 쉬었다가 그날 아침 반드시 돌아야 합니다.** 그래서 이 항목이 가격보다 중요합니다.

- **Supabase 무료 프로젝트의 비활성 일시정지** — 일정 기간 안 쓰면 프로젝트가
  정지된다고 알려져 있습니다. **조건과 기간을 반드시 확인하세요.**
  사실이면 **캠프 당일 아침에 앱이 안 뜨는 시나리오**가 생깁니다.
  회피는 가능하지만(유료 전환, 주기적 핑) **회피책이 필요하다는 것 자체가 비용입니다.**
- **Firebase** 에 같은 성격의 정지가 있는지도 함께 확인하세요.
- **Cloud Functions 가 유료 플랜을 요구하는지** — 이 구조는 Functions 가 꼭 필요하진
  않습니다(동기화를 GAS 가 하고 앱이 DB 를 직접 읽음). 그래도 확인해 두면 선택지가 넓어집니다.
- **결제 수단 등록**은 기술 판단이 아니라 **행정 승인 사항**입니다. 교회 계정에
  카드를 등록해야 하는 플랜이면 그 절차부터 확인하세요.

> 확인 방법: 두 회사의 가격 페이지를 브라우저에서 직접 열어 보세요.
> `firebase.google.com/pricing` · `supabase.com/pricing`
> (작업 환경에서는 두 도메인이 막혀 있어 확인하지 못했습니다.)

## 6. 사진은 어떻게 하나

지금은 Google Drive 입니다 (D-010). **그대로 두는 것을 권합니다.**

저장소를 옮기면 이원화되거나 기존 사진을 전부 이전해야 합니다. 사진은
**갤러리에서 한 번 불러오면 끝**이라 응답 속도 문제의 원인이 아니었습니다.
느린 것은 시트를 여러 번 왕복하는 **메타데이터 조회**였습니다.
문제가 아닌 곳을 고치면 위험만 늘어납니다.

## 넘어갈 기준

감으로 정하지 않기 위해 **수치**로 적어 둡니다. 하나라도 걸리면 도입을 검토합니다.

- [ ] **부트스트랩(첫 화면) 응답이 3초를 넘는다** — 현장 와이파이에서 실측 기준
- [ ] `me` / `progress.list` 가 **2초를 넘는다**
- [ ] 조장들이 동시에 체크할 때 **`LockService` 대기 실패(20초 초과)가 실제로 발생**한다
- [ ] GAS **일일 실행 시간 한도**(소비자 계정 90분/일)에 근접한다
- [ ] 참가자가 **300명을 넘는다** — 시트 전체 읽기 비용이 선형으로 늘어난다

지금 상태에서는 **`test-perf.js` 가 왕복 횟수를 고정**하고 있으므로,
최적화가 되돌아가면 배포 전에 테스트가 먼저 잡아냅니다.

**아직 아무도 실측하지 않았습니다.** 기준을 적어 두고 재지 않으면 기준이 없는 것과 같습니다.

## 만약 도입한다면 — 순서

1. 프로젝트 생성. **1단계는 제품 무관** — §5 의 운영 리스크만 확인하고 고릅니다
2. 공개 데이터 5개 탭만 미러링. 권한은 **읽기 전체 허용 / 쓰기 전면 금지**
3. GAS 에 1분 시간 트리거로 전량 덮어쓰기 동기화 함수 추가
4. 앱의 `bootstrap` 만 DB 에서 읽도록 교체.
   **실패하면 기존 GAS 경로로 자동 폴백** — 이게 있어야 되돌릴 수 있습니다
5. 실측. 위 기준 수치가 실제로 좋아졌는지 확인
6. 여기까지로 충분하면 **멈춥니다.** 개인정보 미러링과 토큰 발급은
   그때도 부족할 때만 손댑니다 — 그리고 **그 지점이 제품을 고를 때**입니다(§2)
