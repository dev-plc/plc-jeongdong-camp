## B-01. 조장이 완료를 찍으면 관리자가 실시간으로 확인 — 조별 진행 파악

**우선순위**: P2 · **시점**: 10/24 캠프 당일 전 (10/10 캠티교육 때 조장 사용법과 함께 점검)

### 지금 되는 것

`/admin.html` → 진행 현황 탭(`admin.progress.board`)이 이미 표를 그립니다.

- 행: `(참여 일자, 조 배정)` 조합마다 한 줄. 조이름 · 조장 이름 · 인원수 표시
- 열: 답사 4개 지점
- 칸: `대기 / 도착 / 완료` 칩 + 그 조의 **방문 순서**(`2번째`) + 도착·완료 시각
- 조마다 배정 코스가 달라 방문 순서가 다른 것까지 반영됨

### 없는 것 (이번 작업 범위)

1. **자동 갱신** — 지금은 탭을 다시 눌러야 새로 읽습니다. 관리자가 화면을 띄워 두면
   알아서 갱신되어야 합니다.
2. **변화 알림** — 어떤 조가 방금 완료를 찍었는지 눈에 띄지 않습니다.
   마지막 조회 이후 바뀐 칸을 강조하거나, 상단에 "방금 2조가 배재학당 완료" 식으로 흘려 줍니다.
3. **전체 요약** — 표만 있고 한눈에 보는 지표가 없습니다.
   `전체 12개 조 중 5개 조가 3지점 이상 완료` / `평균 진행 2.4지점` 같은 줄이 위에 필요합니다.
4. **지연 감지** — 늦는 조를 자동으로 짚어 주지 않습니다.
   `Timeline` 의 답사 구간과 `Checkpoints.체류시간분` 으로 예상 시각을 계산해,
   기준보다 늦은 조를 색으로 표시합니다. **현장에서 실제로 쓰이는 건 이 기능**입니다 —
   "지금 누구를 도우러 가야 하나"에 답하는 화면이어야 합니다.

### 설계 메모

- **폴링으로 충분합니다.** GAS 에는 푸시(웹소켓·SSE)가 없습니다. 관리자 화면이 열려 있는 동안만
  20~30초 간격으로 `admin.progress.board` 를 다시 부르면 됩니다.
  조가 12개 안팎, 관리자가 한두 명이므로 GAS 실행 할당량에 부담이 없습니다.
- **탭이 백그라운드일 때는 폴링을 멈춥니다** (`document.hidden`). 현장에서 배터리와 데이터를 아껴야 합니다.
- **변화 감지는 클라이언트에서** — 직전 응답과 비교해 `completedAt` 이 새로 생긴 칸을 찾습니다.
  서버에 "마지막 조회 이후" 개념을 넣으면 관리자가 여럿일 때 서로의 조회에 영향을 받습니다.
- 지연 판단 기준(몇 분 이상 늦으면 경고)은 하드코딩하지 말고 `Config` 에 둡니다
  (예: `PROGRESS_DELAY_WARN_MIN = 15`). 당일 현장에서 조정할 수 있어야 합니다.
- 조장 화면에는 손대지 않습니다. 기록 주체는 조장 그대로입니다(D-006).

### 열린 질문

- 관리자가 **현장을 돌아다니며 폰으로 볼지, 본부에서 노트북으로 볼지**에 따라 레이아웃이 달라집니다.
  폰이면 표가 아니라 조별 카드가 낫습니다.
- 조장에게 "관리자가 보고 있다"를 알릴 필요가 있는지 — 없으면 만들지 않습니다.

## B-02. 버전 기반 자동 새로고침 — **필수**

**우선순위**: P1 · **시점**: 배포 직후 (캠프 당일 전에 반드시)

### 왜 필수인가

정적 파일이 GitHub Pages + Cloudflare 두 겹으로 캐시됩니다. **캠프 당일 급히 고친 내용이
참가자 폰에 반영되지 않는 상황**이 실제로 생깁니다. 80명에게 "새로고침 해주세요"를
전파할 방법이 현장에 없습니다. 그날 앱이 낡은 채로 굳으면 손쓸 수가 없습니다.

지금은 `bootstrap` 응답만 `sessionStorage` 에 5분 캐시하고(`BOOTSTRAP_TTL`),
**JS·CSS 파일 자체의 캐시에는 아무 대응이 없습니다.**

### 할 일

1. **버전 스탬프** — `Config` 시트에 `APP_VERSION` 을 두고 `bootstrap` 에 실어 보냅니다.
   시트 값이므로 **배포 없이** 관리자가 숫자만 올려 전원 새로고침을 강제할 수 있습니다.
   이게 이 설계의 핵심입니다 — 당일 현장에서 코드 배포는 못 해도 시트 한 칸은 고칩니다.
2. **프론트 비교** — 첫 로딩 시 받은 버전을 기억해 두고, 이후 `bootstrap` 응답의 버전이 다르면
   갱신이 필요하다고 판단합니다.
3. **주기적 확인** — 관리자 화면의 폴링(B-01)과 별개로, 참가자 앱도 몇 분 간격으로
   가볍게 버전만 확인합니다. `document.hidden` 이면 멈춥니다.
4. **캐시를 실제로 뚫기** — `location.reload()` 만으로는 부족할 수 있습니다.
   `index.html` 이 스크립트를 `?v=` 쿼리로 부르게 하고, 새 버전을 받으면 그 쿼리를 바꿔
   다시 로드합니다.

### 반드시 지킬 것

- **작업 중인 내용을 날리지 않습니다.** 탐험일지를 쓰던 중에 강제로 새로고침하면 글이 사라집니다.
  작성 중 텍스트를 `localStorage` 에 임시 저장해 두고 복구하거나,
  강제 대신 **"새 버전이 있습니다 · 새로고침"** 배너를 띄워 사용자가 누르게 합니다.
  → 기본은 **배너 방식**, `Config.FORCE_RELOAD = TRUE` 일 때만 강제. 당일 사고 대응용 스위치입니다.
- **Service Worker 는 쓰지 않습니다.** 캐시를 더 잘 다룰 수 있지만, SW 자체가 캐시되어
  "낡은 SW 가 낡은 앱을 계속 서빙하는" 더 나쁜 상태에 빠질 수 있습니다.
  이 규모에는 단순 버전 비교가 맞습니다.

### 배포 절차에도 반영

`DEPLOY.md` 에 추가할 것:

- 프론트를 고쳐 푸시한 뒤 → `Config.APP_VERSION` 을 올린다
- Cloudflare → Caching → **Purge Everything** 한 번 실행
- 두 가지를 세트로 하지 않으면 반쪽만 갱신됩니다

### 열린 질문

- 버전 값을 **손으로 올릴지(시트), 커밋 해시로 자동 주입할지**.
  자동이 정확하지만 배포 없이 못 바꿉니다. **둘 다** 두는 게 답일 수 있습니다 —
  빌드가 넣는 기본값 + 시트가 덮어쓰는 수동 값.
- 확인 주기: 캠프 당일만 짧게(2분), 평소엔 길게(30분)로 나눌지.
