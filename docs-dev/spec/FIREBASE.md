# Firebase 도입 설계 (이번 캠프 **미적용**)

> **상태**: 설계만. 이번 정동 캠프에는 넣지 않습니다 (D-017).
> 다음 캠프나 `classfinder` 개선 때 꺼내 쓸 수 있게 판단 근거까지 적어 둡니다.

## 왜 이 문서가 있나

`classfinder.plch.kr` 을 같은 구조(GAS 웹앱 + 구글 시트)로 운영해 본 결과 **응답이 느렸습니다.**
추측이 아니라 운영 경험입니다. 그래서 "시트를 원본으로 두되 가운데에 DB 를 끼우는" 구조를
검토했고, 결론은 **읽기 미러(read mirror)** 입니다.

이번엔 안 넣습니다. 대신 GAS 쪽 왕복 횟수를 실제로 줄였습니다(D-017 표).
아래 [넘어갈 기준](#넘어갈-기준) 수치에 걸리면 그때 이 문서대로 진행하면 됩니다.

---

## 권장 구조 — 읽기 미러, 단방향

```
[쓰기]  앱 ──→ GAS ──→ 구글 시트   (지금과 똑같이. 원장은 시트다)
                        │
                        └─ 변경 감지 ──→ Firestore   (단방향 복제)

[읽기]  앱 ──────────────→ Firestore  (빠름. 시트를 거치지 않음)
```

핵심은 **화살표가 한 방향**이라는 것입니다.

### 왜 양방향이 아닌가

양방향으로 만들면 같은 레코드를 시트와 Firestore 양쪽에서 고칠 수 있게 되고,
그 순간 **충돌 해결 규칙**이 필요해집니다. "누가 이겼는가"를 정하는 로직은
행정팀이 시트를 직접 고치는 이 프로젝트의 운영 방식과 정면으로 충돌합니다.

무엇보다 **"시트가 원장"이라는 전제 자체가 깨집니다.** 그러면 장애 시
"시트만 보면 된다"는 복구 경로(→ `ARCHITECTURE.md`)를 잃습니다.
단방향이면 Firestore 는 언제든 **버리고 다시 만들 수 있는 캐시**입니다. 이 성질이 중요합니다.

## 동기화 트리거 — 세 가지 선택지

| 방식 | 지연 | 장점 | 단점 |
|---|---|---|---|
| **GAS 시간 트리거 (1분)** | 최대 1분 | 구현이 가장 단순. 실패해도 다음 회차가 복구 | 1분 지연. 변경이 없어도 계속 도는 낭비 |
| **`onEdit` 단순 트리거** | 즉시 | 사람이 시트를 고친 순간 반영 | **웹앱이 쓴 값에는 안 걸린다**(단순 트리거는 사람 편집만). 실행 시간 제한이 짧다 |
| **쓰기 시점 동시 기록** | 즉시 | 지연 없음. 앱이 쓴 것은 확실히 반영 | 쓰기 경로가 느려짐. Firestore 실패 시 롤백 문제 |

**권장: 시간 트리거(1분) + 쓰기 시점 동시 기록의 조합.**
앱이 쓴 것(`Progress`·`Journal`)은 쓰는 김에 같이 밀어 넣고,
사람이 시트를 직접 고친 것(`Participants`·`Config`)은 1분 트리거가 주워 갑니다.
`onEdit` 은 웹앱 쓰기를 못 잡으므로 **단독으로는 쓰지 않습니다.**

동기화는 **전량 덮어쓰기(full replace)** 로 시작하는 편이 안전합니다.
이 규모(참가자 160명, 탭 10개)에서 증분 계산의 복잡도가 이득보다 큽니다.

## 🔴 가장 큰 걸림돌 — 인증

이 프로젝트의 로그인은 **이름 + 연락처 뒷 4자리**입니다 (D-003).
Firebase 계정이 아니라 **명단(시트)** 이 신원의 근거입니다.

앱이 Firestore 를 **직접 읽으려면** 보안 규칙(Security Rules)이 필요하고,
보안 규칙이 사람을 구분하려면 요청에 **Firebase 인증 토큰**이 실려 있어야 합니다.
지금의 자체 HMAC 토큰은 Firebase 가 알아보지 못합니다.

그래서 이 경로가 필요합니다.

```
앱 → GAS 로그인(이름+뒷4자리) → GAS 가 Firebase Custom Token 발급
   → 앱이 그 토큰으로 signInWithCustomToken()
   → 이제 Firestore 를 규칙 아래에서 직접 읽을 수 있음
```

**커스텀 토큰을 발급하려면 서비스 계정 개인키로 JWT 에 서명해야 합니다.**
GAS 에서 `Utilities.computeRsaSha256Signature` 로 가능은 하지만, 문제는 **키 보관**입니다.

- 스크립트 속성에 넣으면 → 스크립트 편집 권한이 있는 사람이 전부 볼 수 있습니다.
  지금은 행정팀도 시트를 열고, 시트에서 스크립트 편집기로 들어갈 수 있습니다.
- 별도 프로젝트로 분리하면 → 관리 대상이 하나 늘고 배포 절차가 복잡해집니다.

**대안**: Firestore 를 **공개 읽기 전용**으로 두고 개인정보를 아예 안 올리는 방법.
`Config`·`Checkpoints`·`Timeline`·`Notices` 만 미러링하면 애초에 공개해도 되는 데이터라
인증 문제가 통째로 사라집니다. **먼저 이쪽부터 하는 것을 권합니다** — 이득의 상당 부분
(첫 화면 로딩)을 인증 문제 없이 가져갑니다.

## 비용

- **Spark(무료) 플랜으로는 Cloud Functions 를 못 씁니다.** 카드 등록이 필요한
  **Blaze(종량제)** 로 올려야 합니다. 교회 계정에 결제 수단을 등록하는 일이므로
  기술 판단이 아니라 **행정 승인 사항**입니다.
- 다만 이 구조는 Cloud Functions 가 **꼭 필요하지는 않습니다.** 동기화를 GAS 가 하고
  앱이 Firestore 를 직접 읽으면 Functions 없이 굴러갑니다. → Spark 로도 가능.
- **이 규모의 예상치**: 참가자 160명 × 캠프 2회. 한 사람이 하루에 화면을 200번 본다고
  넉넉히 잡아도 문서 읽기 `160 × 200 ≈ 32,000회/일`.
  Spark 무료 한도가 **하루 50,000 읽기**이므로 **무료 한도 안**입니다.
  쓰기는 진행 체크·일지뿐이라 하루 수천 건 수준으로 한도(20,000)에 한참 못 미칩니다.
- 결론: **비용은 이 규모에서 걸림돌이 아닙니다.** 걸림돌은 인증과 운영 복잡도입니다.

## 사진은 어떻게 하나

지금은 Google Drive 입니다 (D-010). **그대로 두는 것을 권합니다.**

Firebase Storage 로 옮기면 저장소가 둘로 갈라지거나(이원화), 기존 사진을 모두
이전해야 합니다. 사진은 **갤러리에서 한 번 불러오면 끝**이라 응답 속도 문제의
원인이 아니었습니다. 느린 것은 시트를 여러 번 왕복하는 **메타데이터 조회**였습니다.
문제가 아닌 곳을 고치면 위험만 늘어납니다.

## 무엇을 미러링하고 무엇을 안 하나

| 탭 | 미러링 | 이유 |
|---|---|---|
| `Config` | ✅ | 모든 요청이 읽는다. 변경은 드물다 — 캐시 효율 최고 |
| `Checkpoints` | ✅ | 사실상 고정. 읽기만 발생 |
| `Timeline` | ✅ | 고정. 첫 화면에서 바로 필요 |
| `Notices` | ✅ | 자주 읽고 가끔 쓴다 |
| `Courses` / `Teams` | ✅ | 작고 자주 읽는다 |
| `Participants` | ⚠ **개인정보** | 미러링하려면 인증이 먼저다. 연락처는 **절대 올리지 않는다** |
| `Progress` | ⚠ | 실시간성이 필요하면 이득이 크다(B-01과 맞물림). 쓰기 충돌 설계 필요 |
| `Journal` | ⚠ | 승인 상태가 자주 바뀐다. 규칙 설계 필요 |
| `Log` | ❌ | 감사 기록. 앱이 읽지 않는다. 미러링 이득 0 |

**1단계로는 위 5개(`Config`·`Checkpoints`·`Timeline`·`Notices`·`Courses`)만.**
개인정보가 없어 인증 없이 공개 읽기로 갈 수 있고, 첫 화면 로딩이 가장 잦은 요청입니다.

## 넘어갈 기준

감으로 정하지 않기 위해 **수치**로 적어 둡니다. 하나라도 걸리면 도입을 검토합니다.

- [ ] **부트스트랩(첫 화면) 응답이 3초를 넘는다** — 현장 와이파이에서 실측 기준
- [ ] `me` / `progress.list` 가 **2초를 넘는다**
- [ ] 조장들이 동시에 체크할 때 **`LockService` 대기 실패(20초 초과)가 실제로 발생**한다
- [ ] GAS **일일 실행 시간 한도**(소비자 계정 90분/일)에 근접한다
- [ ] 참가자가 **300명을 넘는다** — 시트 전체 읽기 비용이 선형으로 늘어난다

지금 상태에서는 **`test-perf.js` 가 왕복 횟수를 고정**하고 있으므로,
최적화가 되돌아가면 배포 전에 테스트가 먼저 잡아냅니다.

## 만약 도입한다면 — 순서

1. Firebase 프로젝트 생성, Firestore 활성화 (Spark 로 시작)
2. 공개 데이터 5개 탭만 미러링. 보안 규칙은 **읽기 전체 허용 / 쓰기 전면 금지**
3. GAS 에 1분 시간 트리거로 전량 덮어쓰기 동기화 함수 추가
4. 앱의 `bootstrap` 만 Firestore 에서 읽도록 교체.
   **실패하면 기존 GAS 경로로 자동 폴백** — 이게 있어야 되돌릴 수 있습니다
5. 실측. 위 기준 수치가 실제로 좋아졌는지 확인
6. 여기까지로 충분하면 **멈춘다.** 개인정보 미러링과 커스텀 토큰은
   그때도 부족할 때만 손댑니다
