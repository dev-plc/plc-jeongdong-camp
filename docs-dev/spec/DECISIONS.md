# 결정사항 (ADR)

프로젝트 진행 중 확정된 결정을 기록합니다. 변경 시 이 문서를 먼저 고치고 코드를 따라오게 합니다.

---

## D-001. 브랜드 표기: PLI → **PLC**

- **결정**: 캠프 명칭·홍보물·앱 전반에서 `PLI` 대신 `PLC`를 사용한다.
- **배경**: 초기 기획안 PDF와 1차 포스터 시안에 `PLI 성경적세계관 캠프`로 표기되어 있었으나 컨셉이 PLC로 수정됨.
- **영향**: `docs-dev/plan/` 의 원본 PDF는 히스토리 보존을 위해 **수정하지 않는다**. 앱/신규 산출물에서만 PLC를 쓴다.

## D-002. 스택

- **결정**: GitHub Pages(`docs/`) + Cloudflare(DNS/캐시) + Google Apps Script Web App + Google Sheets.
- **배경**: `classfinder.plch.kr` 과 동일 패턴 → 운영 인력이 이미 익숙하고 별도 서버 비용이 없음.
- **영향**: 백엔드는 GAS 단일 엔드포인트(`/exec`). 프론트는 정적 파일만. DB는 스프레드시트 1개.

## D-003. 조장(캠티) 인증 = **이름 + 연락처 뒷 4자리**

- **결정**: 로그인은 `이름 → 연락처 뒷 4자리`. **참여 일자는 묻지 않습니다**(D-027 에서 뺐습니다).
- **대안 기각**: 조별 PIN 발급(배포·분실 대응 운영 부담), 조 코드 + 뒷4자리(입력 단계 증가).
- **참여 일자는 명단에서 읽습니다.** 원래는 화면에서 고르게 했지만 **고르든 말든 결과가
  같았고**(힌트일 뿐 조건이 아님), 첫 회차가 기본 선택돼 있어 오히려 틀린 값이 찍혔습니다.
  서버의 힌트 처리(`hintSession`·`sessionCorrected`)는 남아 있지만 앱은 보내지 않습니다.
- **마스터시트의 이름 표기 대응**: 명단은 동명이인 구분을 위해 이름 뒤에 4자리를 붙여 적습니다
  (`이승천7377`). 참가자에게 그대로 입력하라고 할 수 없으므로, 이름은 구분번호를 뗀 `이승천` 과
  붙은 채로 `이승천7377` 을 모두 받습니다. 화면 표시에서는 구분번호를 자동으로 뗍니다.
- **뒷 4자리 인증 수단은 전환된다** (`Config.LOGIN_ALLOW_NAME_DIGITS`)

  | 시기 | 값 | 인정되는 뒷 4자리 |
  |---|---|---|
  | 명단 작성 중 — 연락처가 임시값(`010-1234-5678`) | `TRUE` | 연락처 마지막 4자리 **또는** 이름 뒤 4자리 |
  | 실제 연락처를 다 채운 뒤 | `FALSE` | 연락처 마지막 4자리 **만** |

  **`TRUE` 는 임시 조치입니다.** 이름 뒤 4자리는 명단을 본 사람이면 누구나 알 수 있어,
  켜 둔 채로는 사실상 이름만으로 로그인되는 것과 같습니다.
  `checkDuplicates()`(명단 점검)가 같은 연락처가 3행 이상 반복되는지로 임시값을 감지해,
  **연락처가 모두 실제 값이 되면 스위치를 내리라고 알려 줍니다.**
- **영향**
  - `Participants` 에 **전체 연락처**를 저장하되, 서버는 뒷 4자리만 비교하고
    **연락처를 응답에 절대 포함하지 않는다**(관리자 API 제외).
  - `이름(구분번호 뗀 것) + 뒷4자리` 조합이 2건 이상이고 참여 일자로도 좁혀지지 않으면
    `AMBIGUOUS` 를 반환하고 운영진 문의를 안내한다.
  - **시도 횟수 제한은 두지 않는다.** 이름+뒷4자리는 원리상 무차별 시도가 가능하지만,
    명단에 없는 사람은 아무것도 못 하고 얻을 수 있는 것은 같은 조 진행 상황과 일지뿐이다.
    반대로 잠금을 걸면 **현장에서 참가자가 못 들어오는 사고**가 나고, 그때 풀어 줄 사람이 없다.
    현장 운영 비용이 더 크다고 판단해 잠금을 뺀다. 실패 기록은 `Log` 에 계속 남긴다.
  - 인증 성공 시 HMAC 서명 토큰(기본 12시간)을 발급한다. 세션 저장소는 쓰지 않는다(GAS 무상태).

## D-004. 탐험일지 갤러리 = **전체 공개 + 승인 큐**

- **결정**: 기본값은 캠프 참가자 **전체 공개**(`Config.GALLERY_SCOPE = ALL`). 단, **관리자 승인 전에는 작성자 본인과 운영진에게만 보인다**(`Config.JOURNAL_REQUIRE_APPROVAL = TRUE`).
- **배경**: 몰입도·경쟁 요소를 살리자는 판단. 다만 초상권/미승인 사진 노출 리스크가 있어 승인 큐를 필수로 둔다.
- **전환 계획**: 운영 중 부담이 크면 `Config` 시트에서 `GALLERY_SCOPE` 를 `TEAM` 으로 바꾸면 **배포 없이 즉시** 조 단위 공개로 전환된다. 코드는 두 모드를 모두 구현한다.
- **영향**: `Journal.상태` 는 `대기 / 승인 / 반려 / 삭제` 4상태. 목록 API는 항상 승인 여부 + 스코프 필터를 적용한다.
- **`ALL` 의 실제 범위**: 같은 **참여 일자** 안에서만 공개한다. 10/31 와 11/07 의 기록은 서로 섞이지 않는다.

## D-005. 회비 = **조회 전용(읽기)**

- **결정**: 앱은 회비 **상태만 보여준다**. 결제·정산·수납 체크는 앱에서 하지 않는다.
- **배경**: 금전 기록 쓰기 권한을 조장에게 주면 정산 분쟁 소지가 있음. 수납은 행정가(이휘영/이승천 목사)가 시트에서 직접 관리.
- **영향**
  - 참가자: 본인 `회비상태` 만 조회.
  - 조장: 조원 회비상태 목록 조회(금액·납부수단은 미노출, 상태 라벨만).
  - 쓰기 API 없음. `Config.SHOW_FEE = FALSE` 로 화면에서 완전히 숨길 수 있다.

## D-006. 답사 진행 기록은 **조 단위**, 기록 주체는 **조장**

- **결정**: 4개 지점의 도착/완료는 조장만 기록한다. 개인별 체크인은 만들지 않는다.
- **배경**: 기획안의 "조별 활동 / 조별 시간 분산" 원칙. 80명 개인 체크인은 현장에서 병목.
- **영향**: `Progress` 의 단위 키는 `(참여 일자, 조 배정, 지점코드)`.
- `조장` 뿐 아니라 `스태프` · `사역자` 도 같은 기록 권한을 갖는다 — 현장에서 대신 눌러야 할 때가 있다.

## D-007. 조별 코스는 **배정 코스(A~D)** 로 회전

- **결정**: `Participants.배정 코스` 에 `A코스(배재 시작)` 처럼 적고, `Courses` 시트가
  코스명 → 지점 방문 순서(`CP1,CP2,CP3,CP4`)를 매핑한다.
- **배경**: 기획안 리스크 — "현장에 다수가 몰려 설명이 어려움". 조마다 시작 지점을 달리해 분산.
- **영향**
  - 앱의 코스 화면은 `Checkpoints.기본순번` 이 아니라 소속 조의 배정 코스 순서를 따른다.
  - 코스명이 정확히 일치하지 않아도 **앞글자(A/B/C/D)** 가 같으면 매칭한다(표기 흔들림 대응).
  - 조원끼리 배정 코스가 어긋나면 `checkDuplicates()` 가 경고한다.

## D-008. 신청·모집은 앱 범위 밖

- **결정**: 참가 신청은 기존 신청 폼(9/6 오픈)에서 받고, 확정 명단만 `Participants` 시트로 넘긴다.
- **영향**: 앱에는 회원가입이 없다. 명단에 없는 사람은 로그인 불가 → "운영진에게 문의" 안내.

## D-009. 탐험일지 수정·삭제 권한 = **작성자 본인 / 소속 조장 / 전체 관리자**

- **결정**: 하나의 탐험일지(글·사진)를 고치거나 지울 수 있는 사람은 세 부류다.
  1. **작성자 본인** (`Journal.참가자ID` 일치)
  2. **작성자가 속한 조의 조장** — `(참여 일자, 조 배정)` 이 모두 같아야 한다. 다른 조·다른 날짜의 일지에는 손댈 수 없다.
  3. **전체 관리자** (관리자 PIN 로그인) — 모든 일자·모든 조.
- **삭제는 소프트 삭제**: 행을 지우지 않고 `상태 = 삭제` 로 바꾼다. 사진 파일도 Drive에서 즉시 지우지 않고
  휴지통으로 보낸다(`setTrashed(true)`). 오삭제 복구와 감사 추적을 위해서다.
- **수정 시 재승인**: `JOURNAL_REQUIRE_APPROVAL=TRUE` 인 동안 **승인된 일지를 고치면 다시 `대기` 로 내려간다**.
  승인 후 내용을 바꿔치기해 공개하는 경로를 막기 위해서다. 관리자가 고칠 때는 승인 상태를 유지한다.
- **모든 수정·삭제는 `Log` 시트에 남는다**(행위자 ID, 대상 일지ID, 이전 상태).

## D-010. 사진 저장은 Google Drive

- **결정**: 탐험일지 사진은 시트가 아니라 Drive 폴더(`Config.DRIVE_FOLDER_ID`)에 저장하고, 시트에는 파일 ID만 기록한다.
- **영향**: 업로드 전 클라이언트에서 긴 변 1600px / JPEG 0.8 로 리사이즈하여 GAS 요청 크기 제한(약 50MB, 실질적으로는 훨씬 작게)과 Drive 용량을 아낀다.

## D-011. **캠프 대상**과 **참여 일자**는 서로 독립적인 축이다

- **배경**: 행정팀 마스터시트 초안을 받아 보니 `캠프 대상`(청년부/장년부)과
  `참여 일자`(10/31·11/07)가 별개 컬럼이고, **청년부이면서 11/07에 참여하는 인원**이 있었다.
  기획안만 보고 "청년=10/31, 장년=11/07" 로 합쳐 두었던 초기 설계는 틀렸다.
- **결정**: 두 축을 분리한다.
  - **참여 일자**가 앱의 "회차" 다 — 타임라인, 갤러리 공개 범위, 조 구분이 모두 이 기준.
  - **캠프 대상**은 표시용·공지 타깃팅용 속성으로만 쓴다.
- **영향**
  - 조를 특정하는 키는 `(참여 일자, 조 배정)` 조합이다. 10/31의 "1조" 와 11/07의 "1조" 는 다른 조.
  - 별도의 `조ID` 를 두지 않는다. 행정팀이 ID를 따로 관리할 필요가 없고,
    마스터시트의 `1조` 표기를 그대로 쓸 수 있다.
  - 참여 일자 값은 `Config.SESSION_1` / `SESSION_2` 에 두어, 날짜가 바뀌어도 배포 없이 고칠 수 있다.
    단 **명단의 표기와 글자까지 같아야 한다**(`checkDuplicates()` 가 검사한다).

## D-012. 시트 헤더는 **마스터시트 표기를 그대로** 쓴다

- **결정**: `Participants` 의 헤더를 행정팀 마스터시트와 글자까지 동일하게 맞춘다
  (`회비 대상(2만/3만)` 같은 어색한 이름도 그대로).
- **배경**: 행정팀이 자기 시트를 복사해 붙여넣는 것이 실제 운영 흐름이다.
  코드 쪽 이름이 예쁘자고 헤더를 바꾸면 매번 수작업 매핑이 생긴다.
- **영향**: 컬럼 이름은 `gas/Sheets.gs` 의 `COL` 상수 한 곳에만 둔다.
  헤더를 바꿔야 하면 `COL` 만 고치면 된다. 코드는 열 순서가 아니라 헤더 텍스트로 컬럼을 찾으므로
  행정팀이 열을 추가하거나 순서를 바꿔도 동작한다.


## D-013. 화면 문구는 **시트 헤더를 따라간다**

- **결정**: 앱에 보이는 항목 이름(`캠프 대상` · `참여 일자` · `조 배정` · `입금 여부` ·
  `여행자 보험 가입` · `배정 코스`)을 하드코딩하지 않고, `bootstrap.labels` 로 내려받아 쓴다.
  값의 출처는 `gas/Sheets.gs` 의 `COL` 상수, 즉 마스터시트 헤더 그 자체다.
- **배경**: 행정팀은 시트에서 부르는 이름으로 대화한다. 앱이 "회비", 시트가 "입금 여부" 라고
  하면 문의를 주고받을 때마다 번역이 필요하다.
- **영향**: 헤더를 바꾸려면 `COL` 한 곳만 고치면 시트 스키마와 앱 문구가 함께 따라온다.
  프론트는 `L('feeStatus', '입금 여부')` 처럼 항상 기본값을 함께 둬서, 서버가 옛 버전이어도 깨지지 않는다.

## D-014. 행정팀 동기화 스크립트를 **같은 프로젝트에 통합**

- **결정**: 행정팀이 쓰던 탭 간 동기화 스크립트를 `gas/MasterSync.gs` 로 저장소에 넣고,
  앱과 한 Apps Script 프로젝트에서 함께 돌린다. 동작(이름 기준 끌어오기·양방향 동기화·헤더 검증)은 그대로다.
- **왜 통합하나**: 스프레드시트 하나에 스크립트 프로젝트도 하나다. 따로 둘 수 없다.
- **조정한 것 셋** — 그냥 합치면 조용히 깨지는 지점들이다.
  1. **`onOpen` 은 한 개만 살아남는다.** 같은 이름의 함수가 두 파일에 있으면 나중에 로드된 것만
     남아 다른 메뉴가 사라진다. `onOpen` 은 `Setup.gs` 에만 두고 동기화 메뉴는
     `addMasterSyncMenu_(ui)` 로 붙인다.
  2. **헤더 검증이 앱 시트를 전부 빨갛게 칠한다.** `Config` · `Journal` 등은 헤더 체계가 아예 달라
     "마스터에 없는 헤더" 로 잡힌다. `appManagedSheetNames_()` 로 검증·동기화 대상에서 제외한다.
  3. **원장 탭 이름이 다르다.** 행정팀은 `마스터`, 앱은 `Participants` 를 찾았다.
     `resolveSheetName_()` 이 `마스터` → `Participants` → `명단` 순으로 찾아 양쪽을 같은 탭에 붙인다.
- **무한루프 걱정 없음**: `onEdit` 같은 단순 트리거는 사람이 편집할 때만 실행된다.
  웹앱이 시트에 쓰는 값에는 반응하지 않는다.

## D-015. 서버 없이 도는 **데모 페이지**를 빌드 산출물로 둔다

- **결정**: `docs/demo.html` 을 `tools/build-demo.js` 로 생성해 저장소에 커밋한다.
  실제 `app.css` / `api.js` / `ui.js` / `app.js` / `admin.js` 를 **그대로 인라인**하고
  `fetch` 만 가로채 가짜 백엔드에 물린다.
- **왜 화면을 복제하지 않나**: 데모용으로 화면을 따로 만들면 반드시 실제와 어긋난다.
  네트워크 계층만 갈아 끼우면 데모에서 본 것이 곧 실제 화면이다.
- **영향**: 앱을 고친 뒤에는 `node tools/build-demo.js` 를 다시 돌린다.
  `deferInit()` 이 `DOMContentLoaded` 등록 줄을 찾지 못하면 빌드가 실패하므로,
  그 줄을 바꾸면 조용히 낡은 데모가 남는 대신 즉시 드러난다.

## D-016. 부서=일자가 1:1이어도 **두 축은 합치지 않는다**

- **배경**: 운영은 청년부·장년부를 별도로 굴린다. 원칙적으로 **청년부 10/31, 장년부 11/07** 로
  일자와 부서가 1:1이다.
- **결정**: 그래도 `캠프 대상` 과 `참여 일자` 를 **하나로 합치지 않는다**(D-011 유지).
  코드는 계속 두 축을 따로 본다.
- **이유**: "일부 인원이 섞일 수 있다"는 것이 확인됐다. 1:1을 코드에 박아 두면
  **예외 인원이 생기는 순간 그 사람은 로그인부터 깨진다.** 조 배정·갤러리 범위까지 연쇄로 어긋난다.
  1:1은 *현재 데이터가 어쩌다 그런 상태*일 뿐 규칙이 아니다.
- **대신 바꾸는 것**: 관리자가 보는 화면에만 부서 구분을 더한다.
  - `admin.progress.board` · `admin.fee.board` 응답에 조별 `audience` 를 실어 보낸다.
  - 조의 부서는 **조원 다수결**로 정하고(`dominantAudience_`), 동수면 `혼합`,
    한쪽이 많으면 `청년부 외` 처럼 표시한다.
  - 운영 콘솔에 부서 필터(전체/청년부/장년부)를 둔다. `혼합` 조는 어느 쪽을 골라도 보인다.
- **손대지 않는 것**
  - **참가자 앱**: 참가자는 자기 조만 보므로 부서 구분이 의미 없다.
  - **갤러리 공개 범위**: `참여 일자` 기준을 유지한다. 부서가 섞였더라도
    **같은 날 함께 다닌 사람들**이라 현장 감각과 맞는다.

## D-018. 마스터시트 헤더 표기는 **별칭으로 양쪽을 받는다**

- **배경**: 행정 DB 실물 시트를 확인해 보니 기획 단계 CSV 와 표기가 달랐다.

  | 실제 시트 | 우리가 쓰던 이름 |
  |---|---|
  | `핸드폰` | `연락처` |
  | `만나이` | `나이` |
  | `이전교회` | (없던 열) |

- **왜 위험한가**: 열을 **헤더 글자로** 찾기 때문에(D-012) 이름이 어긋나면
  예외가 아니라 **빈 값**이 된다. 하필 `연락처` 는 로그인에서 뒷 4자리를 대조하는 열이라
  **에러 하나 없이 전원 로그인 실패**가 난다. 현장에서 원인을 찾기 가장 어려운 종류의 고장이다.
- **결정**: 한쪽으로 강제하지 않고 `Sheets.gs` 의 `COL_ALIASES` 로 **양쪽을 모두 인정**한다.
  - `연락처` ≡ `핸드폰` / `휴대폰` / `휴대전화` / `전화번호`
  - `나이` ≡ `만나이` / `만 나이`
- **대안 기각**
  - *코드를 시트에 맞춰 고정* → 행정팀이 헤더를 되돌리면 다시 깨진다.
  - *행정팀에 이름을 바꿔 달라고 요청* → 사람 손을 타고, 파생 탭(회비관리·조편성)의
    수식까지 함께 고쳐야 한다. 캠프 전에 조용히 어긋날 여지가 크다.
- **화면 문구는 시트를 따른다**: 명단에 `핸드폰` 이라 적혀 있으면 앱도 `핸드폰` 이라고
  표시한다(`actualHeader_`). D-013 과 같은 원칙 — 행정팀과 참가자가 같은 말을 쓰게 한다.
- **중복 열 방지**: `setupSpreadsheet()` 의 `ensureHeaders_` 가 별칭을 '있는 것'으로 센다.
  이 처리가 없으면 실물 시트에서 세팅을 돌릴 때 `핸드폰` 옆에 **빈 `연락처` 열**이 생기고,
  값이 없는 쪽이 우선돼 로그인이 다시 막힌다.
- **행정팀 전용 열은 보존**한다. `이전교회` 처럼 앱이 모르는 열은 건드리지 않는다.

## D-020. 시트는 하나로 두고, **주민번호를 없애고 권한을 좁힌다**

D-019(시트 분리)를 대신하는 결정이다.

- **상황**: 행정 DB 의 신청 폼 응답 탭에 주민등록번호가 평문으로 있다.
  보험 가입용으로 받은 값으로 보인다.
- **결정**: 앱은 **현재 행정 DB 에 그대로 붙인다.** 대신 두 가지를 한다.

  1. **원인 제거** — 여행자 보험 가입이 끝나면 주민등록번호 **열을 삭제**한다.
     **`설문지 응답 시트2` 와 `응답 사본` 두 탭 모두**다(처음엔 한 곳만 적었다).
     🔴 **단, `syncFormToNewDb` 가 주민번호로 생년월일·만나이를 계산하므로
     신규DB 동기화를 끝낸 뒤에 지워야 한다**(D-023).
     앱 스키마에는 애초에 그 열이 없다(설계상 들어갈 자리가 없다).
     명단으로 옮길 때 주민번호·이메일은 가져오지 않는다.
  2. **권한 축소** — `appsscript.json` 의 스코프를 좁힌다.

     | 스코프 | 이전 | 이후 |
     |---|---|---|
     | 스프레드시트 | `auth/spreadsheets` (전체) | **`auth/spreadsheets.currentonly`** |
     | 드라이브 | `auth/drive` | 유지 (사진 폴더·공유·휴지통) |
     | 스크립트 | `auth/script.scriptapp` | **삭제** (`ScriptApp` 미사용) |

- **`currentonly` 가 실제 통제 수단이다**: 이 스코프에서는 **붙어 있는 그 문서 하나만**
  열 수 있다. 주민번호 탭이 같은 문서에 있든 없든, 스크립트가 **다른 문서를 읽을
  수단 자체가 없다.** D-019 가 하려던 일을 분리 없이 달성한다.
- **딸린 정리**: `getSpreadsheet_()` 의 `openById` 폴백을 제거했다.
  좁힌 권한 아래에서 동작할 수 없는 죽은 길이라, 남겨 두면 다음 사람이 헛짚는다.
  이 스크립트는 **반드시 시트에 바인딩된 상태**로 배포해야 한다.
- **`drive` 를 못 좁히는 이유**: `drive.file` 은 **앱이 만든 파일만** 다룰 수 있어
  관리자가 지정한 기존 사진 폴더를 `getFolderById` 로 열지 못한다. 지금 좁히면
  사진 업로드가 깨진다. 폴더를 앱이 만들게 바꾸면 가능하므로 별도 검토 사항으로 둔다.
- **⚠ 배포에서 확인해야 하는 것**: `currentonly` + 웹앱 조합은 실제 배포로만 확증된다.
  새 버전 배포 → 권한 재승인 → `?action=health` 와 **로그인 1회**를 확인한다.
  실패하면 `auth/spreadsheets` 로 되돌리고(1줄) 그 사실을 여기 적는다.
- **남는 위험**: 앱 권한보다 **사람 공유 범위**가 더 현실적인 유출 경로다.
  시트를 누구와 공유했는지 주기적으로 점검하는 편이 낫다.

## D-021. 일정 변경은 **배포가 아니라 운영 작업**이다

- **문제**: 일정이 한 주 밀렸을 때 코드의 `SESSION_1/2` 를 고쳤는데도 시트에는 반영되지
  않았다. `seedConfig_` 는 **이미 있는 키를 덮어쓰지 않기** 때문이다
  (`Setup.gs` — 운영 중인 값을 세팅 재실행이 날려 버리면 안 되므로 이 동작 자체는 옳다).
  즉 **한 번 세팅한 뒤로 일정은 코드로 바꿀 수 없다.**
- **결정**: 시트 메뉴에 **`일정 변경`** 을 두고, 회차 날짜는 여기서만 바꾼다.
- **왜 Config 만으로 안 되나**: `참여 일자` 는 표시값이 아니라 **조를 특정하는
  복합키의 한 축**이다(D-011). 이 열을 쓰는 탭이 다섯이다.

  | 탭 | 안 바꾸면 |
  |---|---|
  | `Participants` | 그 사람이 조에 안 잡힘 |
  | `Teams` | 조 메타가 끊어짐 |
  | `Timeline` | 그 날 일정표가 안 뜸 |
  | `Progress` | 기록한 진행 상황이 미아가 됨 |
  | `Journal` | 쓴 일지가 갤러리에서 사라짐 |

- **🔴 반드시 한 번의 매핑으로 치환한다**: 새 1차 라벨이 옛 2차 라벨과 같은 경우가 있다.
  이번이 정확히 그랬다(`10/24·10/31` → `10/31·11/07`). 1차를 먼저 바꾸고 2차를 바꾸면
  **두 회차가 한 값으로 뭉갠다.** 행마다 `{옛값: 새값}` 맵을 한 번만 적용한다.
  (`tools/build-demo.js` 에서 똑같은 실수를 한 적이 있다.)
- **합쳐짐 경고**: 옮겨갈 라벨에 이미 행이 있으면 두 무리가 한 회차로 섞인다.
  실행 전 미리보기에서 탭별로 알려 주고 확인을 받는다.
- **입구는 둘**: 시트 메뉴 `일정 변경` 과 **`Config` 탭 직접 편집**.
  운영진이 "메뉴 말고 Config 에서 하고 싶다"고 해서 `onEdit` 에 붙였다
  (`applyScheduleEdit_`). Config 값만 바뀌고 시트가 안 따라오면 조가 끊어지므로,
  **Config 편집을 감지해 다섯 탭을 함께 바꾼다.**
  한 셀씩 고치는 순서가 곧 순차 치환이라 겹침이 그대로 문제가 되는데,
  **옮겨갈 라벨에 이미 행이 있으면 값을 되돌리고** "2차부터 바꾸세요" 라고 안내한다.
  안내대로 하면 충돌 없이 끝나고, 틀려도 데이터는 안 깨진다.
- **부서는 재배치하지 않는다**: 라벨만 민다. 부서=일자 1:1 은 원칙일 뿐 예외가 있으므로
  (D-016) 사람 배치를 코드가 추측해선 안 된다. 대신 **명단 점검**이 한 회차에 두 부서가
  섞여 있으면 알려 준다 — 차단이 아니라 알림이다.

## D-022. 캐시 때문에 값이 늦게 보이면 안 된다

- **배경**: D-017 성능 작업에서 `CacheService` 5분 캐시를 넣으면서 **원래 없던 반영
  지연을 만들었다.** 그전에는 요청마다 시트를 읽어 지연이 0이었다.
  속도만 보고 대가를 충분히 따지지 않은 것이다.
- **결정**: 캐시는 유지하되 **지연을 없앤다.** 값을 고치는 경로는 둘뿐이므로 둘 다 막는다.
  - 사람이 시트 편집 → `onEdit` 이 `clearConfigCache()` (신규)
  - 관리자 콘솔 → `configSet_` 이 이미 호출 중
- **구현상 함정**: `onEdit` 은 앱 탭이면 `isAppSheet_` 에서 곧바로 return 하는데,
  캐시의 원천(`Config`·`Notices`·`Timeline`·`Checkpoints`·`Courses`)이 전부 앱 탭이다.
  **무효화 훅은 그 return 앞에 놓아야 한다.** 뒤에 놓으면 에러 없이 아무 일도 안 일어난다.
- **남는 예외**: 사람이 직접 친 편집이 아닌 변화(`IMPORTRANGE` 갱신, 수식 재계산,
  외부 API 편집)는 `onEdit` 이 못 잡아 최대 5분 걸린다. 문서에 명시하고
  메뉴의 `캐시 비우기` 를 남겨 둔다.

## D-023. 행정팀 동기화 스크립트를 **한 파일로 합친다**

- **배경**: 시트에서 실제로 돌고 있는 스크립트를 받아 보니, 앞서 통합해 둔
  `MasterSync.gs` 와 **다른 버전**이었다. 기능이 서로 겹치지 않았다.

  | 기능 | 현행본 | 기존 `MasterSync.gs` |
  |---|---|---|
  | `syncFormToNewDb` (설문지 X → 신규DB) | ✅ | ❌ |
  | `syncAllBasicInfoFromDB` (DB참조 → 전체 탭) | ✅ | ❌ |
  | `validateHeaders` | ✅ 마스터+DB참조 기준 | ✅ 앱 탭 제외 |
  | `onEdit` 탭 간 **양방향 동기화** | ❌ | ✅ |

- **왜 합쳐야 하나**: Apps Script 는 파일이 달라도 **전역 스코프를 공유**한다.
  같은 이름의 함수가 둘이면 **나중에 로드된 것만 남는다 — 에러 없이.**
  `onOpen` 과 `validateHeaders` 가 정확히 그 상태였다. 둘 다 붙여넣으면
  메뉴가 사라지거나 검증이 엉뚱하게 돈다.
- **양방향 동기화가 사라진 이유로 추정되는 것**: 운영진이 "원래 됐는데 지금은 안 된다"고
  했는데, 현행본에 `onEdit` 이 없다. 이전 파일을 새 파일로 **교체하면서 잃은 것**으로 보인다.
  통합본이 그 기능을 되살린다.
- **결정**: `gas/MasterSync.gs` 하나에 기능 넷을 모두 담는다.
  - 현행본 로직은 **그대로 옮긴다.** 특히 `parseBirthAndAge_`(주민번호 → 생년월일·만나이)는
    생년 추정 규칙이 기존 데이터와 맞물려 있어 **손대지 않는다**.
  - `onOpen` 은 `Setup.gs` 한 곳에만. 여기서는 `addMasterSyncMenu_` 로 메뉴 4개를 추가만 한다.
  - `validateHeaders` 는 하나로 합친다 — **기준은 마스터+DB참조**(현행본),
    **대상에서 앱 탭 제외**(기존). 제외하지 않으면 앱 탭 9개가 전부 빨갛게 칠해진다.
  - `isSyncExcludedSheet_` 를 만들어 세 순회 함수(전파·기본정보 갱신·헤더 검증)가
    같은 제외 기준을 쓰게 한다. 앱 탭 + `DB참조`·`신규DB`·설문지 응답.

### 역할 분담 — 기본정보는 **DB참조가 주인**

운영진 판단으로 `성별`·`만나이`·`핸드폰` 등 기본정보는 DB참조가 단일 진실이다.
그러면 `onEdit` 이 그 열을 탭 간에 퍼뜨려선 안 된다 — 메뉴 갱신과 서로 덮어쓰며 싸운다.

```
DB참조에 있는 열   →  메뉴 '전체 기본정보 갱신' 만 건드린다
그 밖의 운영 값    →  onEdit 이 탭 간 양방향 전파
(조 배정·역할·입금 여부·배정 코스…)
```

제외 목록을 하드코딩하지 않고 **DB참조 헤더에서 자동으로 뽑는다**(`syncReadonlyHeaders_`).
DB참조에 열이 늘어도 코드를 고칠 필요가 없다. DB참조 탭이 없으면 폴백 목록을 쓴다.

- **주민번호 삭제 순서**: `syncFormToNewDb` 가 주민번호로 생년월일·만나이를 계산하므로
  **신규DB 동기화를 끝낸 뒤에** 지워야 한다(D-020). 이후 신규 신청자는 수동 입력이 필요하다.
- **알려진 한계**: `pushToOtherSheets_` 는 같은 이름의 **첫 행만** 갱신한다.
  마스터 명단이 `이름+구분번호`(`이승천7377`) 표기라 실제 충돌 가능성은 낮다.

## D-024. `onEdit` 은 **셀이 아니라 범위**를 다룬다 / 행 추가는 트리거가 아니라 메뉴

**맥락**: 운영진이 "MasterSync 가 일부 인원만 동기화된다"고 알려 왔다.
시트를 직접 읽어 확인하니 `조편성` 9명은 `조 배정`·`배정 코스`·`핸드폰` 이 전부 차 있는데
마스터에는 `조 배정` 3명, `배정 코스` 2명만 반영돼 있었다. 9명 전원이 마스터에 존재했고
`⚡ 전체 기본정보 갱신` 은 143/145 로 정상이었다. 즉 **메뉴는 멀쩡하고 `onEdit` 만 샜다.**

**원인**: 구글시트는 여러 칸을 붙여넣어도 `onEdit` 을 **한 번만** 부르고 `e.range` 에 범위
전체를 담아 준다. 그런데 코드가 `range.getValue()` — **좌상단 한 칸만** 읽고 나머지를
조용히 버렸다. 에러가 안 나서 아무도 몰랐다. 한 칸씩 직접 친 3건만 살아남은 것이다.

**결정**: `e.range` 를 **범위로 순회**한다. `getValues()` 로 한 번에 읽고 칸마다 처리한다.

- **문서로 덮지 않는다.** "붙여넣기는 안 됩니다"를 매뉴얼에 적는 대신 코드를 고쳤다.
  행정팀의 실제 작업 방식이 열 단위 붙여넣기다. 사용 방식을 코드에 맞추라고 할 수 없다.
- **임계치 `SYNC_MAX_CELLS = 2000`**: 붙여넣기가 수천 칸이면 칸마다 전파하다
  실행 시간 한도에 걸려 **중간에 끊긴다** — 그게 바로 이 버그의 증상이다.
  넘으면 전파를 포기하고 **토스트로 `👥 명단 반영` 을 쓰라고 알린다.**
  일부만 조용히 하느니 안 하고 알리는 편이 낫다.
- **`loadPushTargets_`**: 대상 탭의 헤더·이름 목록을 **한 번만 읽어 재사용**한다.
  칸마다 `getDataRange()` 를 다시 읽으면 범위 순회가 왕복을 폭증시킨다.
  `test-sync.js` 가 붙여넣기 한 번의 시트 읽기 횟수를 고정한다.

### 행 추가(`👥 명단 반영`)는 왜 메뉴인가

"명단이 추가되면 아래로 흘러갔으면 좋겠다"는 요청에 대해, **자동 트리거로 만들지 않았다.**

- **폼 제출은 `onEdit` 이 못 잡는다.** 설치형 `onFormSubmit` 트리거가 따로 필요하고,
  권한 승인과 트리거 관리가 늘어난다. 실시간성이 꼭 필요한 일이 아니다.
- **행 추가는 되돌리기가 번거롭다.** 값 하나가 아니라 행이 생긴다.
- 요청의 핵심은 '자동'이 아니라 **"확인의 편의성"** 이었다.
  그래서 **미리보기(누가 어디에 몇 명) → 확인 → 실행 → 리포트** 로 만들었다.

세부 결정:

- **설문지에서 가져오는 것은 `이름`·`핸드폰` 뿐이다.** `캠프 대상`(부서)은 **비워 둔다** —
  설문의 자기신고를 자동으로 확정하지 않는다. 부서 배정은 운영진 판단이다.
  주민등록번호·이메일은 가져오지 않는다(개인정보는 원천 탭에만 둔다, D-020).
- **새로 만드는 행에는 기본정보도 함께 채운다.** `pullFromMaster_` 는 DB참조 소유 열을
  건너뛰지만(D-023), 빈 행에는 덮어쓸 값이 없고 핸드폰이 비면 실무 탭에서 사람을
  확인할 수가 없다. **기존 행을 고치는 경로는 그대로 DB참조가 주인이다.**
- **역방향은 경고만.** 실무 탭에만 있고 마스터에 없는 이름은 지우지 않는다. 사람이 판단할 일이다.
- **`참가자ID` 는 자동 호출하지 않는다.** `fillParticipantIds` 가 `withLock_` 안에서 돌아
  중첩되면 잠금이 꼬인다. 리포트 마지막 줄에 "`참가자ID 채우기` 를 실행하세요"를 넣었다.
- **`역할`·`참여 일자` 는 채우지 않는다.** 두 열은 `조편성`·설문지 어디에도 없어
  동기화로 만들어 낼 수 없다. 사람이 정해야 한다(`참여 일자` 는 로그인 필수 조건).

## D-025. `onEdit` 전파 경로에서 문서 락을 걷어낸다

**맥락**: 붙여넣기 버그(D-024)를 고친 뒤에도 운영진이 **"조 배정을 빠르게 입력하면
다 스킵된다"** 고 알려 왔다. 확인해 보니 **입력한 칸의 값은 남아 있고, 동기화만
누락**됐다. 그리고 **다 입력한 뒤 그 열을 복사·붙여넣기 하면 전부 반영**됐다.

이 두 사실이 원인을 특정한다. 붙여넣기는 `onEdit` **실행 1번**, 한 칸씩 치는 것은
**실행 N번**이다. 즉 **실행이 겹칠 때만** 깨진다.

**원인**:

```js
var lock = LockService.getDocumentLock();
try { lock.waitLock(3000); } catch (error) { return; }   // ← 여기서 사라진다
```

단순 트리거는 동시에 여러 개가 돈다. 앞 실행이 3초 안에 안 끝나면 뒤 실행은
락을 못 잡고 **조용히 `return`** 했다. 재시도도, 큐도, 토스트도, 로그도 없다.

그리고 한 번의 실행이 실제로 3초를 넘겼다 — `loadPushTargets_` 가 대상 탭마다
`getDataRange()` 로 전체를 읽고, `pullFromMaster_` 는 이름 칸마다 마스터(145×14)를
다시 읽은 뒤 채울 열마다 `setValue()` 를 불렀다. **느림이 곧 유실이었다.**

### 그 락은 무엇을 지키고 있었나 — 아무것도 아니다

- 웹앱의 `withLock_` 은 **`getScriptLock()`**, 여기는 **`getDocumentLock()`** 이었다.
  **애초에 서로 배제하지 않는다.**
- 웹앱은 `Participants` 를 **읽기만** 한다(`readTable_` 3곳). 겹쳐 쓸 일이 없다.
- `onEdit` 끼리의 전파는 편집된 칸마다 **서로 다른 셀**에 쓴다. 같은 셀을 두 실행이
  쓰는 경우는 사람이 같은 칸을 두 번 고쳤을 때뿐이고, 그때는 나중 값이 이기는 게 맞다.
  행을 넣거나 지우지도 않으므로 읽고-고쳐-쓰기 경합이 없다.

**결정**: 전파 경로에서 락을 **없앤다.** 지키는 것 없이 데이터만 버리고 있었다.
락이 진짜 필요한 곳은 `applyScheduleEdit_`(회차 라벨 변경, 5개 탭 수백 행을 읽고
고쳐 씀) 하나뿐이라 `withScheduleLock_` 으로 거기만 감쌌다. **못 잡으면 토스트로
알린다** — 조용한 `return` 은 이 사고의 본질이므로 어디에도 남기지 않는다.

### 큐를 넣지 않은 이유

미반영 편집을 속성에 쌓아 두고 시간 트리거로 처리하는 방법도 있다. 안 했다.
상태가 하나 더 생기고, **그 큐 자체가 조용히 실패할 수 있다.**
버리는 경로를 없애는 편이 확실하다.

### 같이 고친 것

- **`e.source.getActiveSheet()` → `e.range.getSheet()`**. 실행이 밀리는 동안
  사용자가 다른 탭으로 넘어가면 '활성 탭' 은 이미 딴 곳이다. 값은 편집된 범위에서
  읽으면서 헤더는 엉뚱한 탭에서 읽고 있었다.
- **왕복 줄이기** — 락을 없애도 실행이 3초씩 걸리면 30초 한도와 동시 실행 수에 계속
  부딪힌다.
  - `loadPushTargets_`: 먼저 **헤더 행만** 읽어 *편집된 열을 가진 탭*만 남기고
    (`조 배정` 만 고쳤으면 `회비` 는 데이터를 아예 안 읽는다), 남은 탭에서
    **`이름` 열 1열만** 읽는다.
  - `loadMasterIndex_`: 마스터를 **실행당 한 번만** 읽는다. 예전에는 이름 칸마다 다시 읽었다.
  - `flushWrites_`: 쓰기를 모았다가 한 행 안에서 **붙어 있는 열끼리 묶어**
    `setValues()` 한 번으로 내보낸다.
- **예외를 삼키지 않는다**. `console.error` 는 운영진에게 보이지 않는다. 토스트를 띄운다.
  (이 규칙이 개발 중에 바로 값을 했다 — `flushWrites_` 의 루프 버그가 토스트로 드러났다.)

**회귀 방지**: 테스트 하네스의 `LOCKS.available = false` 로 **락을 전혀 못 잡는 상황**을
재현한다. 그 상태에서 한 칸씩 연속 6번 편집해 **전부** 전파되는지 본다.
옛 코드를 되돌리면 이 케이스가 곧바로 빨갛게 뜬다(확인함).
탭별 읽기 횟수(`SHEET_OPS.readsBySheet`)도 고정해 두어 왕복이 다시 늘면 잡힌다.

## D-026. 회차 개수는 상수가 아니라 **Config 에서 찾는다**

**맥락**: 운영진이 **사전답사를 회차로 얹어 앱을 실제로 돌려 보고** 싶어 했습니다.
본 캠프 전에 로그인·조·지점 체크·일지를 현장에서 한 번 굴려 보는 리허설입니다.

그런데 막혀 있었습니다. 원인은 한 줄이었습니다.

```js
function sessions_() {
  [1, 2].forEach(function (n) {          // ← 회차가 2개로 박혀 있다
```

`Config` 에 `SESSION_3` 을 적어도 앱이 읽지 않았습니다. 반대로 **그 위쪽은 이미 열려
있었습니다** — 로그인 화면의 회차 선택, 일정표, 조 키, 명단 점검이 전부 목록을 받아
도는 구조였습니다. 막고 있던 것은 목록을 만드는 함수 하나였습니다.

**결정**: `Config` 의 키에서 `SESSION_<숫자>` 를 **찾아** 번호순으로 돌려준다.

### 🔴 `1..N` 순차 스캔을 쓰지 않은 이유

빈 칸에서 멈추는 방식이 더 짧지만, **`SESSION_2` 를 지우면 `SESSION_3` 이 에러 없이
사라집니다.** 이 프로젝트에서 가장 비싼 실패는 조용한 실패입니다(D-024·D-025 가 둘 다
그것이었습니다). 키를 훑는 쪽은 한 줄 길지만 구멍이 없습니다.
`test-session.js` 가 **중간 회차를 지운 상태**를 직접 재현해 이걸 고정합니다.

### 사전답사를 특별 모드로 만들지 않은 이유

'테스트 모드' 나 `SESSION_TEST` 같은 분기를 두면, 리허설은 **본 캠프와 다른 코드
경로**를 지나게 됩니다. 그러면 리허설에서 통과한 것이 본 캠프에서 통과한다는 보장이
사라집니다. 사전답사는 **그냥 회차 하나**입니다. 로그인도, 조 키도, 지점 체크도,
일지도 본 캠프와 같은 길로 갑니다.

회차가 다르면 조·진행·일지가 이미 격리되므로(D-011, `teamKey_`), 사전답사 데이터가
본 캠프에 섞이지 않습니다. 그래서 **테스트 데이터 정리 메뉴도 만들지 않았습니다**
(운영진 판단). 끝나면 `Config` 의 두 줄을 지우면 로그인 화면에서 사라집니다.

### 왜 `회차 추가` 를 메뉴로 뒀나

`Config` 탭에 두 줄을 손으로 적어도 앱은 읽습니다. 하지만 **`참여 일자` 드롭다운이
안 따라옵니다** — 명단에서 새 회차를 고를 수가 없습니다. 이 뒷정리가 메뉴의 존재
이유입니다. `addSession()` 은 한 번에 합니다:

1. 라벨 중복 검사 — 같은 라벨이 두 회차에 있으면 **조 키가 뭉갭니다**(D-011)
2. `Config` 에 `SESSION_<max+1>` / `_DATE` 두 줄 추가
3. **기존 회차의 일정표 복사** (묻고 나서) — 사전답사는 동선이 같아 이게 있으면 바로 화면이 뜹니다
4. `applyValidation_()` 재호출 — 드롭다운 4곳에 새 라벨
5. 캐시 비우기 + **다음 순서 안내**(참가자ID 채우기 → 조 목록 동기화 → 명단 점검)

번호는 **`max + 1`** 입니다. 중간이 비어 있어도 재사용하지 않아 옛 번호와 부딪히지
않습니다(빈 번호를 정식으로 지운 경우에만 다시 쓰입니다).

### 같이 푼 것

- `changeSchedule()` — 회차 수만큼 묻는다. **치환 맵을 한 번에 적용**하는 구조는 그대로
  뒀다. 새 1차 라벨이 옛 2차 라벨과 같은 경우를 막는 장치다(D-021).
- `applyScheduleEdit_` — `/^SESSION_\d+$/` 로 판별. 충돌 시 **그 라벨을 지금 쓰는 회차
  이름**을 찾아 대 준다("SESSION_2 를 먼저 바꾸세요").
- `checkDuplicates` — `"Config 의 SESSION_1/2 와 다름"` 대신 **쓸 수 있는 회차 목록**을 보여 준다.
- `.seg` (로그인 화면) — `flex-wrap` 이 없어 회차 셋이 한 줄에 눌리면 긴 라벨만 두세 줄로
  접혀 버튼 높이가 어긋났다(390px 에서 `114x46 / 114x46 / 114x69`). 줄바꿈과 최소 폭을 줬다.
  `browser.js` 가 **버튼 높이가 모두 같은지**로 고정한다 — 옛 CSS 로 되돌리면 실패한다(확인함).

## D-027. 카메라만 열리던 사진 업로드 / 로그인 화면의 날짜 선택 제거

사전답사 리허설에서 참가자 앱 두 가지가 걸렸습니다.

### ① `capture` 는 갤러리 선택지를 **없앤다**

```html
<input type="file" name="photo" accept="image/*" capture="environment" hidden>
<span>사진 선택 / 촬영</span>     ← 라벨은 '선택' 을 약속하는데
```

`capture` 가 붙으면 iOS·안드로이드 모두 OS 선택창을 건너뛰고 **카메라를 바로 엽니다.**
사진 보관함 항목이 아예 사라집니다. **화면이 약속한 것을 속성이 금지**하고 있었고,
에러가 안 나므로 "왜 안 되지" 로만 보였습니다.
(같은 화면의 `사진 교체` 입력에는 `capture` 가 없어 거기서는 되고 있었습니다 —
두 입력이 서로 다르게 동작했습니다.)

**결정**: `capture` 를 떼는 대신 **입력을 둘로 나눕니다** — `📷 촬영` / `🖼 갤러리에서 선택`.

- `capture` 만 지우면 OS 선택창이 한 겹 끼어 **카메라가 한 탭 느려집니다.**
  걷는 캠프에서 조장이 현장에서 바로 찍는 경로라 그 한 탭이 아깝습니다.
- 무엇이 될지가 **누르기 전에 화면에 보입니다.** 눌러 봐야 아는 것보다 낫습니다.
- `사진 교체`(수정 화면)는 **그대로 둡니다.** 이미 둘 다 되고, `data-field="photo"` 로
  찾아 쓰는 구조라 입력을 늘리면 `querySelector` 가 첫 번째만 집어 조용히 어긋납니다.

### ② `file.type` 으로 미리 거르지 않는다

```js
if (!file || !/^image\//.test(file.type)) {
  reject(new Error('이미지 파일만 올릴 수 있습니다.'));
```

안드로이드 갤러리·클라우드 피커는 타입을 **빈 값이나 `application/octet-stream`** 으로
넘깁니다. 그러면 사진을 골랐는데도 "이미지 파일만 올릴 수 있습니다" 가 떴습니다.
**카메라 촬영은 항상 `image/jpeg` 라 이 구멍이 드러나지 않았습니다** — ①을 고치는
순간 바로 나타날 자리였습니다.

측정해 보니 **브라우저는 blob 을 바이트로 판별해 디코드합니다** —
타입이 `application/octet-stream` 인 PNG 도 그대로 열렸습니다.
그래서 선검사를 **없앴습니다. 판단의 주인은 디코더**이고, 이미지가 아니면
`img.onerror` 가 받아 "사진을 읽지 못했습니다" 로 안내합니다.

> 처음에는 "타입이 **비어 있을 때만** 통과" 로 고쳤는데, 실제로는 빈 값이 아니라
> `application/octet-stream` 으로 오는 것을 측정에서 확인하고 규칙을 버렸습니다.
> 추측한 규칙이 하나 더 생기느니 검사를 없애는 편이 맞습니다.

### ③ 로그인 화면의 날짜 선택을 뺀다

화면이 스스로 이렇게 적고 있었습니다.

```
날짜를 잘못 골라도 명단이 맞으면 들어갈 수 있습니다.
```

**고르든 말든 결과가 같습니다.** 게다가 **첫 회차가 기본 선택**되어 2차 참가자는 틀린
값이 찍힌 채 들어왔고, 회차를 늘린 뒤로는(D-026) 사전답사까지 같이 떠서 더 헷갈렸습니다.
**아무것도 바꾸지 않는 입력은 화면에서 뺍니다.**

같이 지운 것: `localStorage` 의 `SESSION_KEY` — **쓰기만 하고 아무도 읽지 않았습니다.**
라디오를 미리 채우려던 흔적입니다. `config.js` 의 키도 함께 지웠습니다.

**남긴 것**: 서버의 `hintSession` 처리(`gas/Auth.gs:144`). 앱이 빈 값을 보내도 정상
동작하고, 건드릴 이유가 없습니다.

**알아 둘 것**: 힌트는 **같은 이름 + 같은 뒷 4자리**가 두 회차에 있을 때 후보를 좁히는
데 쓰였습니다. 이제 그런 경우는 `AMBIGUOUS` 로 떨어져 "운영진에게 문의해 주세요" 가
뜹니다. 조용히 엉뚱한 사람으로 로그인시키는 것보다 안전한 실패이고,
`명단 점검` 이 이 충돌을 **미리** 잡아 줍니다.

### 회귀 방지

`browser.js` 62건(+11) · `demo-check.js` 33건(+2).
`capture` 검사, 두 입력 각각으로 넣은 업로드, `사진 빼기` 가 둘 다 비우는지,
타입을 모르는 파일 수용, 로그인 요청에 회차가 안 실리는지를 고정합니다.
**옛 코드로 되돌려 각각 실패하는 것을 확인했습니다.**

지난 회차에 넣었던 로그인 화면 `.seg` 검사 3건은 **걷어냈습니다** — 검사 대상이
사라졌습니다. 없어진 UI 를 지키는 테스트는 초록불만 만들고 아무것도 막지 못합니다.
(`.seg` 자체와 D-026 의 `flex-wrap` 은 관리자 설정의 `공개 범위` 가 계속 씁니다.)

## D-028. 자산 주소에 **내용 해시**를 붙인다 (GitHub Pages 캐시)

**맥락**: 운영진이 "버튼 등 수정사항 반영이 안 된다"고 알려 왔습니다. 마침 다른
프로젝트(`classfinder`·`dgfinder`)의 Cloudflare 캐시 문제를 호스팅 쪽에 문의한
직후라 같은 원인으로 보였습니다. **아니었습니다.**

**확인한 것**:

- `docs/` 에 **`CNAME` 이 없습니다.** 이 앱은 `dev-plc.github.io` 가 직접 서빙합니다.
  **Cloudflare 뒤에 있지 않습니다** — 퍼지할 엣지가 없습니다.
- 서비스 워커 없음(확인함). 가장 골치 아픈 캐시 층은 없습니다.
- `index.html` 이 자산을 **버전 없이** 참조하고 있었습니다.

**진짜 원인은 둘이었습니다.**

① **`demo.html` 을 손으로 고쳤습니다.** 이 파일은 `tools/build-demo.js` 가 만드는
생성물인데 두 번의 작업에서 직접 편집했고, 그래서 `app.css` 에만 넣은 CSS
(`.seg` 의 `flex-wrap`·`.filepick-row`)가 데모에는 통째로 빠져 있었습니다.
**캐시를 아무리 비워도 안 고쳐지는 종류입니다.**

② **GitHub Pages 는 응답 헤더를 바꿀 수 없습니다.** Netlify 의 `_headers` 같은
장치가 없어 `Cache-Control` 을 우리가 정하지 못합니다.

**결정**: 참조 주소에 **파일 내용의 sha1 앞 8자리**를 붙입니다(`tools/stamp-assets.js`).

```
./assets/js/app.js  →  ./assets/js/app.js?v=7847799b
```

내용이 바뀌면 주소가 바뀌어 브라우저가 **무조건 새로 받고**, 안 바뀌면 해시도
그대로라 **캐시를 최대한 재사용**합니다.

### 왜 타임스탬프도 커밋 해시도 아닌가

- **타임스탬프**: 안 바뀐 파일까지 매번 새로 받게 만듭니다. 캐시를 통째로 버리는 셈입니다.
- **커밋 해시**: 스탬프가 만든 변경이 다시 커밋을 바꾸므로 **순환**합니다.

내용 해시는 둘 다 아닙니다.

### 하지 않은 것

- **`<meta http-equiv="Cache-Control">`** — HTTP 로 서빙되는 문서에서 브라우저가
  **무시합니다.** 넣어도 아무 일이 없고, 넣었다는 사실 때문에 원인을 잘못 찾게 됩니다.
- **빌드 파이프라인·GitHub Actions 배포** — 지금은 `main`/`docs` 를 그대로 서빙하는
  구조입니다. 스탬프 하나 때문에 배포 방식을 바꾸면 얻는 것보다 잃는 것이 큽니다.

### 잊는 것을 막는 장치

스탬프는 **반드시 잊습니다.** 그래서 `--check` 모드와 `test-stamp.js` 13건을 뒀습니다.
핵심 케이스는 하나입니다 — **자산을 고치고 스탬프를 안 돌리면 `--check` 가 실패한다.**
실제로 `app.js` 에 한 줄을 넣어 빨간불을 확인했고, 테스트는 끝나면 원래대로 되돌립니다.

곁가지로 `browser.js` 의 라우트 글롭도 고쳐야 했습니다
(`**/assets/js/config.js` → `...config.js*`). 쿼리가 붙으면 글롭이 안 맞아
가짜 API 가 안 물렸고, 실제로 한 건이 빨간불로 잡혔습니다.

## D-029. DB 제품을 **아직 고르지 않는다** (Firebase / Supabase)

**맥락**: 운영진이 Firebase 가격 페이지를 주며 DB 계획 검토를 요청했고,
Supabase 도 후보로 올렸습니다. **아직 결정된 것은 없고**, 규모·사용 인원을 감안한
비교와 프로세스 설계를 원했습니다.

**결정**: **제품을 지금 고르지 않습니다.** 고를 필요가 없기 때문입니다.

### 근거 ① — 1단계는 제품과 무관하다

권장 구조의 1단계는 **공개 데이터 5개 탭**(`Config`·`Checkpoints`·`Timeline`·
`Notices`·`Courses`)만 단방향 복제하는 것입니다(`DATABASE.md`).
**개인정보가 0** 이라 읽기를 전체 공개로 두면 되고, 그러면 **인증이 아예 필요 없습니다.**
인증이 빠지면 두 제품의 차이가 거의 사라집니다.
**차이가 드러나는 지점까지 가서 고르는 것이 맞습니다.**

### 근거 ② — 비용은 결정 요인이 아니다

명단 **145명**, 회차 2~3개, 실사용은 회차당 하루 몇 시간, 쓰기는 하루 수백 건입니다.
이 규모에서 두 제품 모두 무료 한도를 넘길 이유가 없습니다.

> 🔴 **가격 수치는 문서에 쓰지 않았습니다.** 두 회사의 가격 페이지가 작업 환경의
> 네트워크 정책에 막혀 **확인하지 못했습니다**(`CONNECT tunnel failed, 403`).
> 기억으로 채우면 틀린 숫자를 근거로 결정하게 됩니다.
> 이전 `FIREBASE.md` 에 있던 Spark 한도 수치도 같은 이유로 **지웠습니다** —
> 검증한 적 없는 값이었습니다.

### 근거 ③ — 진짜 결정 요인은 인증이고, 지금은 Supabase 가 가깝다

이 프로젝트는 **이미 HMAC-SHA256 으로 토큰에 서명합니다**(`gas/Auth.gs` `sign_`).

- **Supabase**: RLS 가 받는 것은 **HS256 JWT**. 지금 `issueToken_` 에 헤더 세그먼트와
  표준 클레임(`sub`·`role`·`exp`)만 얹으면 됩니다. **있는 것을 모양만 맞추는 수준.**
- **Firebase**: Custom Token 은 **RS256**. 서비스 계정 **개인키**로 서명해야 하고,
  GAS 에 `computeRsaSha256Signature` 로 새로 붙여야 합니다.

데이터 모양도 같은 방향입니다 — 시트는 표고, Postgres 도 표입니다.
조 키 `(참여 일자 + 조 배정)`(D-011)이 SQL 에서는 복합 인덱스지만, 문서형에서는
합성 문서 ID 를 계속 만들어야 합니다(지금 `teamKey_` 가 하는 일이 DB 안으로 들어옴).

**다만 키 보관 위험은 양쪽 다 남습니다.** 행정팀이 스크립트 편집기를 열 수 있으므로
스크립트 속성을 볼 수 있습니다. 대칭키는 유출 시 누구나 토큰을 위조할 수 있고,
개인키도 임의 사용자를 사칭할 수 있습니다. **어느 쪽도 이 문제를 풀어 주지 않습니다.**

### 근거 ④ — 이번 캠프에는 넣지 않는다 (D-017 유지)

캠프가 6주 앞입니다. 저장소를 하나 더 넣으면 **"시트만 보면 된다"는 복구 경로를 잃습니다.**
그리고 원래 불만이었던 응답 속도는 GAS 왕복을 줄여 이미 손댔습니다(D-017 표).

### 고를 때 볼 것

1. **운영 리스크부터.** 무료 프로젝트가 **비활성으로 정지되는지** — 캠프는 몇 주
   쉬었다가 그날 아침 반드시 돌아야 합니다. 이게 가격보다 중요합니다.
2. `DATABASE.md` 의 **실측 기준**(부트스트랩 3초, `me`/`progress.list` 2초,
   `LockService` 대기 실패, 참가자 300명).
   **아직 아무도 재지 않았습니다. 재는 것이 먼저입니다.**
3. 그 다음이 §2 의 인증 구조입니다.

**문서**: `FIREBASE.md` → **`DATABASE.md`** 로 이름을 바꾸고 제품 중립으로 다시 썼습니다.
제품명이 파일명에 박혀 있으면 아직 고르지 않은 것이 고른 것처럼 보입니다.

## D-030. 응답 시간은 **항상 기록**하고, 보여 주기만 토글한다

**맥락**: `DATABASE.md` 에 넘어갈 기준을 수치로 적어 뒀습니다 — 부트스트랩 3초,
`me`/`progress.list` 2초. 그런데 **재는 방법이 없었습니다.**
기준을 적어 두고 재지 않으면 기준이 없는 것과 같습니다.
사전답사가 본 캠프와 같은 경로로 도는 리허설이라(D-026) 실측하기 좋은 기회입니다.

**결정**: `api.js` 의 `call()` 한 곳에서 왕복 시간을 재고, `?perf=1` 로 패널을 띄웁니다.

### 왜 항상 기록하나

비용이 타임스탬프 하나와 배열 push 이기 때문입니다. 반대로 **필요할 때 켜는 방식은
늦습니다** — 느린 일이 벌어진 **뒤에** 켜면 그 순간의 데이터가 없습니다.
캠프 당일 "지금 느린데요" 라는 말이 나왔을 때 바로 숫자를 볼 수 있어야 합니다.

`?perf=1` 은 **보여 주기만** 켭니다. 쿼리가 없으면 패널을 **DOM 에 아예 만들지 않아**
참가자에게는 흔적도 없습니다.

### 🔴 캐시 히트를 표본에서 빼는 이유

`bootstrap` 은 `sessionStorage` 에 담아 둡니다(TTL). 캐시로 돌려준 건을 그대로 세면
**0ms 가 표본에 섞여 중앙값이 거짓이 됩니다.** 그러면 "부트스트랩 3초" 기준이
영원히 통과합니다 — 측정이 아니라 자기 위안이 됩니다.
캐시 건은 따로 세어 건수만 보여 줍니다.

### 왜 서버(`Log` 시트)에 안 쌓나

쓰기가 늘고, **그 쓰기 자체가 측정을 왜곡합니다.** 응답이 느린지 보려고 요청마다
쓰기를 하나 더 얹는 것은 앞뒤가 맞지 않습니다. 기기에만 남기고 **[복사]** 로 꺼냅니다.
현장에서 폰으로 눌러 카톡에 붙여 넣을 수 있어야 실측이 실제로 남습니다.

### 실패도 기록한다

**느린 실패가 오히려 중요한 신호**입니다. 타임아웃 직전에 죽는 요청은 성공 표본에
안 잡히면서 체감은 가장 나쁩니다.

### 새 파일을 만들지 않은 이유

`demo.html` 은 `tools/build-demo.js` 가 `api/ui/app/admin` 을 인라인해 만듭니다.
파일을 늘리면 **생성기도 같이 고쳐야 하고**, 바로 그 드리프트로 한 번 물렸습니다(D-028).
기록은 `api.js`, 패널은 `ui.js` 에 넣어 생성기·HTML·스탬프를 건드리지 않았습니다.

### 만들면서 잡힌 것

패널이 화면 아래에 고정되면서 **로그인 버튼을 덮어 눌리지 않았습니다.**
브라우저 테스트가 `intercepts pointer events` 로 잡아냈습니다.
탭바 위로 올리고 본문에 패널 높이만큼 아래 여백을 주는 방식(데모바와 같은 패턴)으로
고쳤습니다. **측정 도구가 측정 대상을 망가뜨리면 안 됩니다.**

**회귀 방지**: `browser.js` 77건(+15). `?perf` 없이는 패널이 없는지, 캐시 히트가
표본에서 빠지는지, 그리고 **`me` 응답을 일부러 2,200ms 늦춰 기준 초과가 ✗ 로
표시되는지**를 고정합니다 — 기준선이 장식이 아님을 확인합니다.

## D-031. 회차 **활성/비활성** 스위치 + 관리자 콘솔 회차 필터

**맥락**: 사전답사 회차를 만들어 굴려 보니 두 가지가 걸렸습니다.

1. 운영 콘솔의 `조 배정별 진행 현황` 필터가 **`전체 / 청년부 / 장년부`**,
   즉 **부서 필터뿐**이라 사전답사만 따로 볼 수가 없었습니다. 표에는 나오는데
   거를 방법이 없어 본 캠프 조와 섞여 보입니다.
2. 사전답사가 끝난 뒤 그 회차를 **끌 방법이 없었습니다.** Config 행을 지우면
   명단의 `참여 일자` 가 목록에 없는 값이 되어 `명단 점검` 이 오류로 잡습니다.

### 결정 ① — `SESSION_n_ACTIVE`

`Config` 에 회차마다 스위치를 둡니다. **`FALSE` 면 앱 입장에서 없는 회차**입니다.

| | 비활성일 때 |
|---|---|
| **로그인** | **막힙니다.** 왜 막혔는지(회차 이름) 알려 줍니다 |
| 일정표(`timeline_`) | 내려가지 않습니다 |
| `bootstrap.sessions` | **내려갑니다** — `active: false` 를 달아서. 관리자 필터가 써야 합니다 |
| `참여 일자` 드롭다운 | **그대로 있습니다** — 없으면 그 회차 사람을 명단에 적을 수가 없습니다 |
| 시트 데이터 | **그대로입니다.** 되돌리는 것은 Config 한 칸입니다 |

**키가 없으면 활성**입니다. 기존 회차는 행을 새로 넣지 않아도 그대로 돌아갑니다.
`회차 추가` 메뉴는 이 행을 **미리 만들어 둡니다** — 있어야 있는 줄 압니다.

**왜 로그인까지 막나**: 운영진이 고른 동작입니다. "화면에서만 감추기" 로는 사전답사
계정이 본 캠프 당일에도 살아 있습니다. 껐으면 꺼져야 합니다.

**🔴 위험과 방어**: 실수로 본 캠프 회차를 끄면 **그 회차 전원이 못 들어옵니다.**
그래서 `명단 점검` 에 **`⚠ 비활성 회차 인원 (로그인 불가)`** 블록을 넣어
누가 막히는지 이름으로 보여 줍니다. 그 사람만 안 되고 나머지는 멀쩡해서
증상만으로는 원인을 찾기 어려운 종류이기 때문입니다.

### 결정 ② — 관리자 콘솔 회차 필터

`진행 현황` · `회비 현황` 두 화면에 부서 필터와 **나란히** 놓습니다.

- 목록은 `boot.sessions` 에서 만듭니다. **회차를 늘려도 따라옵니다**(D-026).
  회차가 하나뿐이면 고를 것이 없으므로 아예 그리지 않습니다.
- **기본값은 `전체`** — 지금까지의 동작과 같아 놀랄 일이 없습니다(운영진 선택).
- **비활성 회차도 숨기지 않고 `비활성` 표기와 함께 보여 줍니다.**
  껐다고 해서 운영진이 기록을 못 보게 할 이유가 없습니다.
  숨기면 "사전답사 결과가 사라졌다" 가 됩니다.
- `.tabs` 에 `flex-wrap` — 탭이 넷 이상이 되므로 좁은 화면에서 줄을 바꿉니다
  (`.seg` 에서 쓴 방식과 같음, D-026).

### 회귀 방지

`test-session.js` 48건(+14) · `demo-check.js` 42건(+9).

핵심은 **켜고 → 로그인되고 → 끄고 → 거부되고 → 다시 켜면 돌아온다** 는 왕복입니다.
`ACTIVE` 키가 없을 때 활성으로 읽는지, 비활성이 `sessionLabels_()` 에는 남고
`activeSessionLabels_()` 에서만 빠지는지, 일정표에서 빠지지만 `bootstrap.sessions`
에는 실려 가는지도 고정합니다.
콘솔 쪽은 필터 기본값·비활성 표기·회차 선택 시 다른 회차가 사라지는지, 그리고
탭이 넷일 때 가로로 넘치지 않는지를 봅니다.

## D-032. Supabase 읽기 미러 — 1단계는 공개 데이터만

**맥락**: D-029 에서 "제품을 아직 고르지 않는다" 고 했는데, 운영진이 두 제품 모두
이 규모에서 무료 한도 안이고 **인증은 다른 곳에서 해 본 경험이 있다**고 판단해
**Supabase 로 확정**했습니다. 제가 못 가진 정보라 그 판단을 따릅니다.

범위는 **공개 데이터만**입니다. 대상은 `bootstrap_()` 이 내려보내는 것 —
**실측 4,546 bytes** (`timeline` 2,656 · `checkpoints` 1,231 · 나머지 합 659).

### 🔴 먼저 인정한 것

**1단계만 놓고 보면 GitHub 에 정적 JSON 을 두는 편이 더 빠르고 단순합니다.**
4.5KB 를 CDN 에서 받는 것보다 빠를 수는 없습니다. Supabase 로 가는 이유는
**2단계(명단·RLS·실시간)로 이어지기 때문**이지 1단계가 더 좋아서가 아닙니다.
1단계에서 멈출 거라면 정적 파일이 맞습니다 — `DATABASE.md` 에 대안으로 남겼습니다.

### 테이블 하나, JSONB 한 행

1단계의 DB 는 **스키마가 아니라 캐시**입니다. 앱은 이미 `bootstrap` 객체를 통째로
소비하므로, 4.5KB 읽기 미러를 정규화하면 이득 없이 옮길 것만 늘어납니다.
**진짜 테이블 설계는 2단계**에서 합니다 — 그때가 Postgres 를 쓰는 이유가 생기는 지점입니다.

### 언제 미는가 — 훅 재사용 + 하루 1회

- **바뀐 순간**: `isCachedSourceSheet_` 훅(D-022)이 공개 데이터 편집을 이미 정확히
  잡아냅니다. 캐시를 비우는 그 자리에서 같이 밀어 **지연이 없습니다.**
- **하루 1회 트리거**: 정지 방지(ping)와 재푸시를 **한 함수로 겸합니다.**
  요청 자체가 활동이므로 재푸시가 곧 ping 입니다. **별도 ping 함수를 두지 않습니다** —
  같은 일을 하는 코드가 둘이면 하나는 반드시 낡습니다.
- **10분 트리거는 두지 않습니다.** 변경은 훅이 즉시 잡고, 공개 데이터는 캠프 전에
  확정돼 거의 안 바뀝니다. 변경이 없어도 계속 도는 것은 낭비입니다.

### 🔴 정지보다 나쁜 것 — 살아 있는 채로 낡기

앱은 미러를 먼저 읽습니다. 미러가 멈춘 채 살아 있으면 **옛 공지를 계속 보여 줍니다.**
그래서 행에 `updated_at` 을 싣고, **26시간**(하루 1회 + 시차 여유)보다 낡으면
앱이 **미러를 버리고 GAS 로 갑니다.** 트리거가 죽어도 자동으로 예전 동작으로
복구됩니다. 이 가드가 없으면 "미러를 켠 뒤로 화면이 이상한데 원인을 모르겠다" 가 됩니다.

### 되돌리는 법이 한 줄일 것

`config.js` 의 `SUPABASE_URL` 을 비우면 끝입니다(D-017 이 요구한 조건).
GAS 쪽도 스크립트 속성이 비면 **아무 호출도 하지 않습니다** — 설정 전에도 안전합니다.

### 미러가 앱을 멈추면 안 된다

`mirrorPush` 는 `onEdit` 안에서도 불립니다. `muteHttpExceptions` + try/catch 로 감싸고
**절대 던지지 않습니다.** 실패는 `Log` 에 남깁니다. 미러 때문에 사람이 시트를 고치는
일이 막히면 안 됩니다. 테스트가 500·예외 두 경우 모두 `onEdit` 생존을 확인합니다.

### 새 권한

`UrlFetchApp` 을 이 프로젝트에서 **처음** 씁니다. `script.external_request` 와
트리거 설치용 `script.scriptapp` 이 늘어 **배포 후 권한 재승인이 한 번** 필요합니다.

### service key 보관 — 2단계의 숙제

service key 는 프로젝트 전권 키인데 스크립트 속성에 둡니다. 시트에서 편집기를 열 수
있는 사람은 볼 수 있습니다(D-029 와 같은 문제). 1단계는 피해가 공개 데이터 한 테이블로
한정되지만, **2단계에서 같은 프로젝트에 명단 테이블이 생기면 위험이 커집니다.**
그때 키를 GAS 밖으로 빼거나 쓰기 전용 역할을 따로 파야 합니다.

### 계정이 갈리는 것은 무관하다

저장소는 `dev@plch.or.kr`, Supabase 는 `ym@plch.or.kr` 입니다. 앱은 Supabase 를
**URL + anon key 로 된 HTTPS** 로만 부르고 GitHub 연동을 쓰지 않으므로 아무 문제가
없습니다. 다만 정지 해제·키 재발급이 그 계정에서만 되므로 **조직으로 만들고 `dev@` 를
멤버로 초대**해 두기를 권했습니다.

### 실측이 붙는다

`API.perf`(D-030)가 **`bootstrap:supabase`** 와 **`bootstrap`(GAS)** 를 따로 셉니다.
사전답사에서 `?perf=1` 로 **두 경로의 중앙값을 나란히** 봅니다.
이득이 있는지를 말이 아니라 숫자로 확인합니다 — 없으면 한 줄로 되돌립니다.

**회귀 방지**: `test-mirror.js` 25건 신규 + `browser.js` 86건(+9).
설정이 없을 때 호출 0건, 보내는 값이 `bootstrap_()` 과 동일한지, **개인정보가 섞이지
않는지**, 마스터 편집은 밀지 않는지, 500·예외에도 `onEdit` 이 사는지,
그리고 브라우저에서 **미러 우선 → 실패 시 폴백 → 낡으면 폐기**까지 고정합니다.

### 프로젝트 생성 시 "기본을 닫힘으로" (D-032 보강)

Supabase 프로젝트 생성 화면에서 두 가지를 기본값과 다르게 잡았습니다.

- **`Automatically expose new tables` 끄기** — 새 테이블에 Data API 권한을 자동으로
  주지 않습니다. 지금은 테이블이 `app_cache` 하나뿐이라 차이가 없지만,
  **2단계에서 명단 테이블을 만들 때 실수로 공개되는 것**을 구조적으로 막습니다.
  Supabase 자신도 화면에서 끄기를 권합니다.
- **`Enable automatic RLS` 켜기** — 새 테이블에 RLS 를 자동으로 켭니다.
  RLS 가 켜져 있고 정책이 없으면 **아무도 못 읽습니다.** 실수했을 때의 결과가
  "전부 공개" 가 아니라 "아무것도 안 보임" 이 됩니다 — **안전한 실패**입니다.

🔴 **그 결과 SQL 에 `grant` 가 필요해졌습니다.**
**RLS 정책과 테이블 권한(GRANT)은 별개입니다.** 정책은 "어떤 행을 볼 수 있는가"를,
GRANT 는 "테이블에 닿을 수 있는가"를 정합니다. 자동 노출을 끄면 GRANT 가 안 붙으므로
정책만으로는 읽히지 않습니다.

이 조합이 특히 고약한 이유: **에러가 아니라 빈 배열이 옵니다.** 앱은 "미러에 데이터가
없다" 고 판단해 조용히 GAS 로 폴백하고, 겉보기엔 잘 돌아갑니다 — 미러를 켰는데 왜
안 빨라지는지 알 수가 없습니다. `DEPLOY.md` §1-7 에 진단 문구를 같이 넣었습니다.

### 키 형식이 둘이다 — `apikey` 는 항상, `Authorization` 은 JWT 일 때만 (D-032 보강)

프로젝트를 만들고 보니 Supabase 의 API 키 체계가 **둘** 이었습니다.

- **옛 형식**: `eyJhbGci…` — **키 자체가 역할을 담은 JWT** 입니다.
  PostgREST 가 이걸 디코드해 역할을 정하므로 `Authorization: Bearer` 로도 보내야 합니다.
- **새 형식**: `sb_publishable_…` / `sb_secret_…` — **JWT 가 아닙니다.**
  역할은 서버가 키로 판별합니다. Bearer 로 보내면 **JWT 파싱에 걸릴 수 있습니다.**

처음 쓴 코드는 옛 형식만 전제해 `apikey` 와 `Authorization` 을 **항상 둘 다** 보냈습니다.
새 형식 키를 쓰면 실패할 수 있는 자리였습니다.

**결정**: `apikey` 는 항상 보내고, `Authorization` 은 **키가 `eyJ` 로 시작할 때만** 붙입니다
(`supabaseAuthHeaders_`, `api.js` 도 같은 규칙). 두 형식 모두에서 동작합니다.

키 형식을 **설정으로 받지 않고 키 모양에서 판별**합니다. 운영진이 "이건 무슨 형식인가"를
고르게 하면 반드시 틀립니다 — 고를 필요가 없으면 틀릴 수도 없습니다.

`test-mirror.js` 가 두 형식 각각에서 헤더가 어떻게 나가는지 고정합니다.

### `service_role` 도 GRANT 가 필요하다 (D-032 보강 2)

미러 첫 실행이 실패했습니다. 원인은 제가 **쓰는 쪽 권한을 빼먹은 것**이었습니다.

`Automatically expose new tables` 를 껐으므로 새 테이블에는 **어느 역할도 권한이
없습니다.** 저는 `anon` 에 `select` 만 주고, `service_role` 에는 아무것도 주지
않았습니다. **`service_role` 은 RLS 는 우회하지만 테이블 GRANT 는 우회하지 못합니다.**
"service key 는 전권" 이라는 통념이 여기서 어긋납니다 — 전권인 것은 *정책*에 대해서지
*권한*에 대해서가 아닙니다.

읽기와 쓰기 **양쪽 다** 명시해야 합니다.

```sql
grant usage on schema public to anon;          -- 읽기: 앱
grant select on app_cache   to anon;
grant usage on schema public to service_role;  -- 쓰기: GAS
grant all    on app_cache   to service_role;
```

**두 실패의 증상이 다릅니다** — `DEPLOY.md` 에 진단표로 넣었습니다.

- `service_role` 누락 → 미러 갱신이 **실패**하고 `Log` 에 `permission denied` 가 남습니다.
  시끄럽게 실패하므로 찾기 쉽습니다.
- `anon` 누락 → **에러가 아니라 빈 배열**이 옵니다. 앱은 "미러에 데이터가 없다" 고
  보고 조용히 GAS 로 폴백합니다. **겉보기엔 잘 돌아가서** 왜 안 빨라지는지 알 수가 없습니다.

후자가 훨씬 위험합니다. 자동 노출을 끄는 선택(안전한 기본값)이 **조용한 실패를
하나 만들어 냈다**는 것이 이 건의 교훈입니다.

## D-033. "서버 응답을 읽지 못했습니다" — 한 번만 재시도하고, 원인을 나눠 말한다

**맥락.** 운영진이 `서버 응답을 읽지 못했습니다. 배포 설정을 확인해 주세요.` 가
**자주** 뜬다고 알려 왔습니다. 그리고 "가운데 DB(Supabase 미러)가 있으면 해결되느냐"
고 물었습니다.

**진단.** 이 메시지는 `api.js` 의 `JSON.parse(text)` 가 던질 때만 뜹니다. 곧
**응답은 정상적으로 도착했는데 본문이 JSON 이 아닌 경우**입니다(연결 자체가
끊기면 "네트워크 연결을 확인해 주세요" 로 갈라집니다).

그런데 `doPost`(`gas/Code.gs`)는 **어떤 경우에도 JSON 을 돌려줍니다** — 본문 파싱
실패도 `jsonErr_`, 라우팅 예외도 `jsonErr_` 입니다. 그러므로 JSON 이 아닌 본문은
**스크립트 밖에서** 온 것이고, 남는 것은 셋뿐입니다.

1. 구글의 HTML 오류 페이지 — 동시 실행/할당량 초과, 일시적 장애
2. 구글 로그인 안내 HTML — 배포 액세스 권한이 "모든 사용자" 가 아님
3. 빈 본문 — `/exec` → `script.googleusercontent.com` 리다이렉트 중 끊김

**"자주" 라면 2번이 아닙니다.** 2번이면 항상 떴을 것입니다. 자주 뜨지만 가끔은 되는
것은 1·3번, 곧 일시적 장애입니다.

### 미러는 이 문제를 절반만 덮는다 — 그리고 새 문제를 만든다

| 호출 | 미러(D-032) 적용 후 |
|---|---|
| `bootstrap` | ✅ Supabase 에서 옴. GAS 가 죽어도 첫 화면은 뜬다 |
| `auth.login`·`me`·`progress.*`·`journal.*`·`fee.status` | ❌ 전부 GAS 그대로 |

**새로 생기는 문제**: 예전에는 첫 화면부터 에러라 "서버가 이상하다" 가 최소한
분명했습니다. 미러가 붙으면 **껍데기는 멀쩡히 뜨고 로그인만 실패**합니다 —
"앱은 되는데 왜 안 들어가지" 가 되어 원인 파악이 **더** 어려워집니다.
**미러는 읽기 캐시이지 가용성 대책이 아닙니다.** 이 구분을 흐리면 안 됩니다.

### 그래서 재시도를 넣는다 — 한 번만

지금까지 재시도가 **한 군데도 없었습니다**. 일시적 장애 한 번이 그대로 사용자
화면의 에러가 됐습니다. 캠프 당일 145명이 동시에 로그인하면 가장 아플 지점입니다.

- 비-JSON·5xx·빈 본문·네트워크 실패면 **600ms 뒤 한 번만** 다시 보냅니다.
- **두 번은 두지 않습니다.** 진짜 장애일 때 기다리는 시간만 3배가 됩니다.
- 서버가 제대로 답한 오류(`{ok:false}`)는 재시도하지 않습니다 — 다시 보내도 같습니다.

### 🔴 `journal.create` 만은 재시도하지 않는다

`journalCreate_`(`gas/Journal.gs:171`)에는 **멱등 키가 없습니다.** `nextId_` 로 새 ID 를
만들어 행을 추가하고, 사진이 있으면 `savePhoto_` 가 Drive 에 **하나 더** 올립니다.
첫 요청이 실제로는 성공했는데 응답만 못 받은 경우 재시도는 **일지와 사진을 중복
생성합니다.** 나머지는 읽기이거나 같은 값을 다시 쓰는 set 의미라 안전합니다.

**허용 목록이 아니라 거부 목록(`NO_RETRY`)으로 둡니다.** 액션이 늘 때 허용 목록에서
빠뜨리면 재시도가 조용히 빠지고, 빠진 것은 아무도 눈치채지 못합니다. 위험한 쪽을
명시하는 편이 낫습니다.

멱등 키를 넣는 쪽이 정답이지만 GAS·시트·Drive 세 곳을 건드려야 해서 캠프 전에 넣을
변경이 아닙니다. **남은 숙제입니다.**

### 말이 틀리면 엉뚱한 곳을 본다

예전 메시지는 무조건 "배포 설정을 확인해 주세요" 였습니다. 자주 뜨는 것은 배포
문제가 아닌데 그렇게 말했고, 그래서 이 질문이 나왔습니다. 이제 나눕니다.

| 응답 | 메시지 | 재시도 |
|---|---|---|
| 본문에 `accounts.google.com`·`ServiceLogin` | 배포의 액세스 권한이 "모든 사용자" 인지 확인 | 안 함 |
| 그 밖의 비-JSON·5xx·빈 본문 | 서버가 잠시 응답하지 않았습니다. 잠시 뒤 다시 | 한 번 |

상태 코드와 본문 앞 200자를 `console.warn` 에 남깁니다. 이것이 없으면 사후에
원인을 확인할 방법이 없습니다.

### 빈도를 숫자로 잡는다

`API.perf`(D-030)에 **재시도 건수**를 더했습니다. `perfText` 에 `· 재시도 N건` 으로
찍힙니다. 사전답사에서 `?perf=1` 로 **"자주" 가 실제로 몇 건인지** 잡힙니다 —
지금까지는 체감뿐이라 고쳤는지 아닌지도 확인할 수 없었습니다.

## D-034. Config 의 날짜 셀이 `Sat Oct 31 2026 …` 로 새어 나가던 문제

미러 행(`app_cache`)을 확인하다 발견했습니다.

```json
"sessions":[{"n":1,"date":"Sat Oct 31 2026 00:00:00 GMT+0900 (한국 표준시)", ...}]
```

원인은 `getConfig_`(`gas/Sheets.gs`)가 시트의 **Date 셀에 그대로 `String()`** 을
씌운 것입니다. 시트에서 `2026-10-31` 로 보이는 칸도 값은 Date 객체입니다.

**앱 화면에는 영향이 없습니다** — `session.date` 를 쓰는 곳이 없습니다(로그인 회차
선택을 D-027 에서 뺐습니다). 문제는 GAS 쪽입니다. `일정 변경`(`gas/Setup.gs`)이 이
문자열을 **프롬프트 기본값**으로 보여 주므로, 운영진이 확인만 눌러도 **그 쓰레기
문자열이 Config 에 다시 써집니다.** 읽기만 하던 값이 쓰기로 돌아오는 경로였습니다.

`TZ = 'Asia/Seoul'` 가 이미 있으므로 `getConfig_` 에서 `Utilities.formatDate` 로
`yyyy-MM-dd` 를 만듭니다. Date 가 아닌 값은 손대지 않습니다.

고친 뒤 메뉴 **`미러 지금 갱신`** 을 한 번 돌려야 미러 행도 정상값이 됩니다.

## D-035. 실패에 **이름**을, 왕복 시간에 **서버 시간**을 붙인다

사전답사 전 첫 실측(2026-09-18, 4G)에서 나온 숫자입니다.

| 액션 | 중앙 | 최대 | 실패 |
|---|---|---|---|
| `progress.set` | 14,875ms | **61,147ms** | **8/15** |
| `admin.progress.board` | 27,010ms | 34,913ms | **3/3** |
| `me` | 26,532ms | 49,872ms | 1/3 |
| `bootstrap:supabase` | **824ms** | 824ms | 0 |

미러는 잘 돕니다. **같은 4G 에서 Supabase 가 824ms 라는 것이 네트워크가 멀쩡하다는
증거**이므로, 나머지 숫자는 전부 서버 쪽입니다.

### 이 표로는 고칠 곳을 정할 수 없었다

두 가지가 빠져 있었습니다.

**1. 실패에 이름이 없다.** `실패 8건` 이 전부였습니다. 락 경합인지, 토큰 만료인지,
마감(`CLOSED`)인지 구분이 안 되는데 셋은 고치는 곳이 완전히 다릅니다.

**2. 30초를 누가 썼는지 모른다.** 브라우저에서 잰 왕복 시간뿐이라, 서버가 30초를
쓴 것인지 대기열에서 기다린 것인지 알 수 없었습니다. 전자는 코드를, 후자는
동시성 구조를 고쳐야 합니다.

### 재시도 수가 이미 하나를 말해 줬다

47건 중 실패 21건인데 **재시도는 1건**입니다. 재시도(D-033)는 비-JSON·5xx·네트워크
실패에만 걸리므로, **실패 20건은 서버가 JSON 으로 오류를 제대로 답한 것**입니다.
곧 D-033 이 고친 계열이 아닙니다. 계측을 붙여 둔 덕에 붙이자마자 하나가 걸러졌습니다.

### 고친 것

- **응답 봉투에 `ms` 를 싣는다** (`gas/Code.gs`). `doGet`·`doPost` 진입에서
  `__reqStart` 를 찍고 `jsonOk_`·`jsonErr_` 가 경과 시간을 함께 내려보냅니다.
  **실패 응답에도 싣습니다** — 느린 실패가 오히려 중요한 신호입니다.
  락 타임아웃이라면 여기가 약 20,000ms 로 나옵니다(`withLock_` 의 `tryLock(20000)`).
- **실패를 코드별로 센다** (`api.js`). `실패 8건(SERVER_ERROR 7 · UNAUTHORIZED 1)`.
- **중앙값 옆에 서버 시간을 붙인다** — `중앙 26532ms(서버 2100ms)`.
  **이 둘의 차이가 대기·전송 시간**이고, 그 차이가 어디를 고칠지 정합니다.
- `perfRecord` 의 꼬리 인자들을 옵션 객체로 바꿨습니다. 인자가 일곱 개가 되면
  호출부에서 `false, false, 0` 같은 자리 맞추기가 생기고 반드시 틀립니다.
- `ms` 가 없는 응답(아직 새 버전을 배포하지 않은 GAS)에서도 그대로 돕니다.
  서버 칸만 비고 측정은 남습니다.

### 아직 정하지 않은 것

원인은 **확정하지 않았습니다.** 가장 유력한 후보는 `withLock_` 의
`LockService.getScriptLock()` 이 **쓰기 전체를 직렬화**하는 것이고,
20초 타임아웃이 정상 JSON 오류로 나가므로 재시도에 안 걸리는 것도 맞아떨어집니다.
다만 락을 잡지 않는 `admin.progress.board` 가 3/3 실패에 27~35초라는 점은
락만으로 설명되지 않습니다. **추측으로 고치지 않고 다음 실측을 기다립니다.**

## D-036. 요청에 **시간 상한**을 둔다 — 원인을 몰라도 피해는 묶는다

### 실행 로그가 서버와 락을 배제했다

D-035 의 실측을 Apps Script **실행 로그**와 대조했습니다.

| | 서버 (실행 로그) | 폰 (실측) |
|---|---|---|
| 최대 | **6.306초** | **61.1초** |
| 대부분 | 1~3초 | 중앙 13~27초 |

`withLock_` 락 타임아웃 가설은 **틀렸습니다.** `tryLock(20000)` 이 실패해도 예외를
`doPost` 가 받아 정상 응답하므로, 실행은 "완료됨" 에 **20초 넘는 기간**으로 남습니다.
그런 실행이 하나도 없습니다. **`getScriptLock()` 을 조별로 쪼개지 않은 것이 다행입니다.**

상태='실패' 필터로도 확인했습니다. **`doPost`·`doGet` 실패 0건.** 걸린 것은
`onEdit` 14건(9/17 오전 — 동기화 버그를 고치기 전. `d75c34a` 이후로는 없음),
`registerNewMembersFromForm` 4건(**`gas/` 에 없는 행정팀의 기존 스크립트**.
3일 연속 실패 중이라 따로 볼 건), `setupSpreadsheet` 1건뿐입니다.

```
폰 ──────── 27~61초 ────────> [???] ──── 2초 ────> Apps Script
```

**원인은 아직 모릅니다.** D-035 의 계측이 다음 실측에서 요청마다 서버 시간을
짝지어 주므로 그때 갈립니다. **추측으로 고치지 않습니다.**

### 그래도 지금 고치는 것

`call()` 에 시간 상한이 **없었습니다.** 요청이 멎으면 무한정 기다립니다.
조장이 지점 완료를 누르고 61초 동안 화면이 멎는 일이 실제로 일어났습니다.
원인을 아는 것과 무관하게, 캠프 현장에서 이건 그 자체로 문제입니다.

`bootstrapFromMirror` 의 `AbortController` + `clearTimeout` 짜임을 그대로 씁니다.

### 🔴 상한은 시도마다가 아니라 **호출 전체**에 둔다

시도마다 15초를 주면 재시도(D-033)와 겹쳐 최악 30초가 됩니다. 상한을 두는 의미가
반감됩니다. 그래서 `call()` 전체에 예산 하나를 두고 각 시도는 **남은 예산**만 씁니다.

```
call 시작 ┬─ 시도1 (남은 15.0초) ─ 3초 만에 비-JSON
          ├─ 0.6초 대기
          └─ 시도2 (남은 11.4초)        ← 총 대기는 언제나 예산 이하
```

첫 시도가 예산을 다 쓰면 재시도할 시간이 없으므로 재시도하지 않습니다.
**"총 몇 초 안에 끝난다" 가 한 값으로 말해집니다.**

이 구분은 실제로 검사됩니다 — 예산을 시도마다로 되돌리면 같은 케이스가
900ms 에서 **1,505ms** 로 늘어 테스트가 깨지는 것을 확인했습니다.

### 🔴 사진이 실린 요청은 예산이 다르다

이 변경의 유일한 진짜 위험입니다. 일지는 리사이즈된 JPEG 를 base64 로 싣습니다
(긴 변 1600px·품질 0.8). **전송 자체가 오래 걸리는 것이 정상**이라 15초로 자르면
4G 에서 사진이 아예 안 올라갑니다. `body.photo.dataBase64` 가 있으면
`UPLOAD_TIMEOUT`(60초)을 씁니다 — 조건 하나로 읽히고, 액션 목록을 따로 관리하지 않습니다.

`journal.create` 는 이미 `NO_RETRY` 입니다(D-033). 끊긴 뒤 자동 재시도가 없습니다.

### 🔴 끊긴 요청은 `TIMEOUT` 으로 따로 센다

```
progress.set — 15건 · 중앙 14875ms(서버 2100ms) · 실패 8건(TIMEOUT 6 · SERVER_ERROR 2)
```

**`TIMEOUT` 이 대부분이면 전송 경로 문제가 확정됩니다.** 이 값 하나가 다음 단계를
정합니다. 끊기만 하고 이름을 안 붙이면 원인이 오히려 흐려집니다.

### 되돌리는 법

`config.js` 의 **`REQUEST_TIMEOUT` 을 `0`** 으로 두면 상한이 사라지고 예전 동작
그대로입니다. `AbortController` 가 없는 환경에서도 상한 없이 돕니다.

## D-037. 진행 기록을 **낙관적으로** 반영한다 (DB 2단계 · 단계 A)

운영진이 **교육관리 프로젝트의 검증된 패턴**을 집안 표준으로 제시했습니다.
핵심은 한 줄입니다.

> **쓰기는 언제나 시트가 먼저, DB 가 나중.** 앱은 DB 를 직접 쓰지 않는다.
> 어긋나면 시트가 이긴다 — 주기 트리거가 시트 값으로 DB 를 맞춘다.
> 읽기는 반대로 Supabase 에서 바로.

정동캠프에서 이 패턴이 닿는 곳은 **진행(progress)** 입니다. 실측에서 가장 아팠던
경로이기도 합니다 — `progress.set` 15건 중 8건 실패, 최대 61초.

이 항목은 그 첫 단계인 **낙관적 UI** 입니다. DB 와 무관하게 단독으로 돕니다.

### 왜 이것이 먼저인가 — 근거는 실측에 있다

예전 코드는 버튼을 잠그고 서버를 기다렸습니다. 그게 61초 멎던 화면입니다.

그리고 다음 단계(쓰기 사본)는 `progress.set` 에 `UrlFetchApp` 호출을 **하나 더**
얹습니다. 실행 로그에서 `mirrorPushNow` 가 12.5초 걸린 것을 봤습니다(bootstrap
전량이라 무겁지만). **낙관적 UI 가 먼저 들어가야 그 추가 지연이 화면을 멎게
하지 않습니다.** 순서가 취향이 아니라 계측에서 나왔습니다.

### 되돌리는 것이 핵심이다

누르면 즉시 반영하고, **실패하면 이전 상태로 되돌립니다**(`app.js` `onProgressClick`).
화면이 거짓말한 채로 남지 않는 것이 이 구조의 전제입니다 — 집안 패턴의
`previous` 롤백과 같습니다.

### 🔴 늦게 온 옛 응답이 새 화면을 덮지 않는다

이제 느린 응답을 **전제**하므로, 두 번 누르면 응답이 순서를 바꿔 도착할 수
있습니다. 발행 순번(`progressSeq`)을 들고 **자기보다 최신 요청이 있으면 옛 응답을
버립니다.** 없으면 1.5초 늦게 온 옛 응답이 새 상태를 덮어씁니다 — 테스트에서
순서를 뒤집어 재현했습니다.

### 🔴 시각은 기기 로컬 파츠로 만든다

`toISOString()` 은 UTC 입니다. `UI.hhmm` 이 `T(HH):(MM)` 만 읽으므로 그대로 쓰면
**9시간 어긋난 시각**이 잠깐 화면에 뜹니다. `UI.localIso` 가 기기 오프셋으로
만듭니다. 서버 응답이 오기 전 몇 초라도 틀린 시각을 보여 주면 안 됩니다.

### 서버 규칙을 그대로 흉내 낸다

`applyProgressLocal` 은 `progressSet_`(`gas/Code.gs`)과 같은 규칙을 씁니다 —
도착·완료는 **최초 시각만** 남기고, 대기는 둘 다 비웁니다. 규칙이 어긋나면
응답이 왔을 때 화면이 튑니다.

### 저장 중임을 숨기지 않는다

화면은 이미 바뀌었지만 아직 서버에 안 갔습니다. 칩에 `· 저장 중` 을 붙이고
카드를 흐리게(`.cp.is-saving`) 둡니다. 숨기면 그것도 거짓말입니다.

### 발견한 것 — 상태를 바꾸면 점수·메모가 지워진다

`progressSet_` 의 `patch` 는 `'퀴즈점수': score`·`'메모': str_(body.memo)` 를 **항상**
씁니다. 앱은 `API.progressSet(code, status)` 로 둘을 보내지 않으므로, 조장이 상태를
누를 때마다 **운영진이 시트에 적어 둔 점수·메모가 빈 값으로 덮입니다.**
앱 화면에는 안 보여서 드러나지 않았습니다. 이번 범위 밖이라 그대로 두되
낙관적 반영도 **같은 동작을 흉내 냅니다** — 화면과 서버가 어긋나면 안 됩니다.
별도로 고쳐야 합니다.

## D-038. 진행 쓰기 사본 — 시트가 먼저, DB 가 나중 (DB 2단계 · 단계 B)

집안 표준(교육관리 프로젝트)의 **②** 를 옮겼습니다.

> 쓰기는 언제나 시트가 먼저, DB 가 나중. 앱은 DB 를 직접 쓰지 않는다.
> 어긋나면 시트가 이긴다.

`progressSet_` 이 `Progress` 탭에 쓴 뒤, 같은 값을 `progress_cache` 에 밀어 넣습니다.

### 🔴 사본이 실패해도 요청은 성공이다

원장은 시트입니다. 사본이 실패했다고 조장에게 "기록 실패" 를 보여 주면,
**시트에는 들어갔는데 실패라고 말하는** 더 나쁜 거짓말이 됩니다.
`mirrorProgressPush_` 는 `mirrorPush` 와 같은 규칙으로 **절대 던지지 않고**
`Log` 탭의 `mirror.progress` 행에만 남깁니다.

### 🔴 락 밖에서 민다

`withLock_` 은 `LockService.getScriptLock()` — **스크립트 전체를 직렬화**합니다.
락을 쥔 채 `UrlFetchApp` 을 기다리면 캠프 당일 다른 조장 여덟 명이 그만큼 줄을 섭니다.
그래서 `withLock_` 이 목록을 **돌려주게** 구조를 바꾸고, 푸시는 락을 놓은 뒤에 합니다.

이건 말로만 두면 언제든 되돌아갑니다. 하네스의 `getScriptLock` 스텁이 **보유 상태를
기록**하고 `UrlFetchApp` 스텁이 호출 시점의 보유 여부를 함께 남기도록 고쳐,
**테스트가 실제로 검사**합니다. 푸시를 락 안으로 되돌리면 그 테스트가 깨집니다(확인함).

### `supabaseUpsert_` 로 뽑았다

`mirrorPush` 의 몸통(fetch · upsert 헤더 · 상태코드 판정 · 절대 안 던짐 · `logEvent_`)이
그대로 다시 필요했습니다. 복사하지 않고 뽑았습니다 — **같은 일을 하는 코드가 둘이면
하나는 반드시 낡습니다.** `mirrorPush` 도 이제 이걸 씁니다.

### 🔴 빈 시각은 `null` 이다

`progressList_` 는 시각이 없으면 `''` 를 줍니다. `timestamptz` 컬럼에 `''` 를 넣으면
Postgres 가 거절합니다 — 그러면 그 조의 사본이 **통째로** 실패합니다.
`str_(p.arrivedAt) || null` 로 바꿉니다. 테스트가 이 값을 직접 봅니다.

### 집안 패턴과 다른 점 — RPC 대신 upsert + CHECK

교육관리는 RPC(`set_attendance_batch`)를 씁니다. 여기서는 upsert 에 `CHECK` 제약을
붙였습니다 — 검증이 상태값 하나뿐이라 RPC 를 세울 이득이 없습니다.

**대신 지우기를 못 합니다.** 시트에서 사라진 행이 DB 에 남습니다.
그래서 **단계 C(주기 동기화)는 선택이 아니라 필수**입니다. 이 점을 알고 미룹니다.

화이트리스트는 두 겹입니다 — `ENUM.PROGRESS`(GAS)와 `progress_status_ck`(DB).
상태값을 늘리려면 **SQL 을 먼저** 열어야 합니다. 거꾸로 하면 사본만 조용히 실패합니다.

### `progress_meta` 는 단계 C 로 미뤘다

앞선 설계에서는 B 도 동기화 시각을 `app_cache` 에 같이 쓰기로 했었는데 뺐습니다.
요청이 하나 더 늘어 **핫 패스가 두 배**가 되는데, 그 값을 쓰는 것은 단계 D 뿐이고
의미도 "주기 동기화가 건강한가" 라 트리거 쪽에 있는 것이 맞습니다.

## D-039. 안 보낸 필드는 덮어쓰지 않는다 — 상태 변경이 점수·메모를 지우던 문제

D-037 에 "별도로 고쳐야 한다" 고 남겨 둔 데이터 손실입니다.

### 어떻게 지워졌나

`progressSet_` 의 `patch` 가 **퀴즈점수와 메모를 항상** 실었습니다.

```js
var score = '';                     // 안 보내면 '' 그대로
…
'퀴즈점수': score,
'메모': str_(body.memo),            // str_(undefined) === ''
```

앱은 `API.progressSet(code, status)` 로 **두 인자만** 보내고, `JSON.stringify` 는
값이 `undefined` 인 키를 **아예 싣지 않습니다.** 그래서 서버는 그 키를 못 받는데도
빈 값으로 덮었습니다. **조장이 지점 상태를 누를 때마다 운영진이 시트에 적어 둔
점수·메모가 지워졌습니다.**

코스 화면이 그 둘을 그리지 않아 **오래 드러나지 않았습니다.** 손실은 운영콘솔의
진행 보드에서만 보입니다. 낙관적 UI(D-037)를 만들며 서버 규칙을 한 줄씩
흉내 내다 발견했습니다 — 흉내 내지 않았으면 지금도 몰랐을 것입니다.

### 고친 방법 — 새 코드가 아니라 키를 빼는 것

`updateRow_`(`gas/Sheets.gs`)는 **현재 행을 먼저 읽고 `patch` 에 있는 키만**
덮어씁니다. 그러므로 키를 빼기만 하면 기존 값이 남습니다.

```js
var hasScore = body.score !== undefined;
…
if (hasScore) patch['퀴즈점수'] = score;
```

**`appendRow_` 는 `patch` 에 없는 컬럼을 `''` 로 채우므로 새 행은 그대로입니다.**

### 🔴 안 보냄 ≠ 비우기

운영진이 점수를 **지우고 싶을 때는 지울 수 있어야** 합니다. 그래서
`score: null` 이나 `score: ''` 를 **명시적으로** 보내면 지금처럼 비웁니다.
"키가 없다" 와 "빈 값을 보냈다" 를 다르게 취급하는 것이 이 수정의 전부입니다.

### 서버와 `applyProgressLocal` 은 짝이다

낙관적 UI 는 서버 동작을 그대로 흉내 내야 합니다 — 어긋나면 응답이 왔을 때 화면이
튑니다. 그래서 `applyProgressLocal` 도 **일부러 같이 지우고 있었습니다**(D-037).
서버가 보존하게 됐으므로 여기도 보존합니다. **한쪽만 고치면 이번엔 반대 방향으로
어긋납니다.**

### 안 보이는 값은 안 지켜진다 — `data-score`

이 버그가 오래 살아남은 이유는 **점수·메모가 화면 어디에도 없었기 때문**입니다.
카드에 `data-score` 속성 하나를 답니다. 표시가 아니라 **확인용**입니다 —
테스트가 보고, 현장에서 개발자 도구로도 봅니다. 화면은 바꾸지 않았습니다.

가짜 서버(`browser.js`)는 처음부터 점수를 보존했습니다. 즉 **앱만 지우고 있어
둘이 어긋난 상태였는데 아무 테스트도 잡지 못했습니다** — 볼 수 없었기 때문입니다.

## D-040. 시트에는 **진짜 Date**, 통신에는 ISO — 시각 표기를 통일한다

운영진이 시트의 `도착시각` 칸을 보고 알려 왔습니다.

```
2026-09-19T10:12:31+09:00
```

읽기 어렵습니다. 그리고 더 나쁜 것은 **이게 글자라는 점**입니다 — 텍스트라
정렬·필터·수식이 전부 안 먹습니다. 날짜처럼 보이지만 날짜가 아니었습니다.

### 시트용과 통신용을 나눈다

| | 함수 | 값 |
|---|---|---|
| **시트 셀** | `nowStamp_()` | `new Date()` — 진짜 날짜 |
| **통신(앱·미러)** | `nowIso_()` | `2026-09-19T10:12:31+09:00` |

읽는 쪽은 **이미 전부 `toIso_` 를 거칩니다**(`progressList_`·`progressBoard_`·
`serializeJournal_`·`activeNotices_`). `toIso_` 는 Date 를 받으면 ISO 로 바꿔 주므로
**통신 형식은 한 글자도 바뀌지 않습니다.** 그래서 앱·미러·정렬(`localeCompare`)이
그대로 돕니다. 새 파서를 만들 필요가 없었습니다.

운영진이 그 칸에 직접 글자를 적어도 `toIso_` 가 그대로 흘려보냅니다 — 섞여 있어도 됩니다.

### 🔴 서식을 입혀야 "통일" 이 된다

`TIME_FORMAT = 'yyyy-mm-dd hh:mm:ss'` 를 **모든 시각 칸에 같게** 입힙니다
(`Participants.등록일시`·`Progress`의 셋·`Journal`의 셋·`Notices`의 둘·`Log.일시`).

**이미 쓰던 시트에도 돌려야 합니다.** 그 칸들은 ISO 글자를 담고 있어 '일반'·'텍스트'
서식입니다. 서식을 안 고치면 Date 를 넣어도 엉뚱하게 보입니다. 그래서 초기 세팅뿐
아니라 **메뉴 `시각 표기 통일`** 로도 언제든 다시 입힐 수 있게 뒀습니다.

### `Timeline` 의 시작·종료는 대상이 아니다

그건 **시점이 아니라 시각(HH:mm)** 입니다 — "09:30 에 모인다" 는 날짜가 없습니다.
`toHm_` 가 따로 다루고 있고, 여기에 날짜 서식을 입히면 오히려 틀립니다.
통일한다고 성격이 다른 것까지 같게 만들면 안 됩니다.

### 🔴 이미 쌓인 값도 같이 바꾼다 (보강)

처음에는 서식만 입히고 "기존 값은 새로 기록될 때부터 바뀐다" 로 뒀는데,
**그게 답이 되면 안 되는 상황**이었습니다. 운영진 시트에는 이미 ISO 글자가 쌓여
있었고, 그대로 두면 한 칸에 글자와 날짜가 **섞입니다.** 그건 통일이 아닙니다.

`convertTimeTextToDates_()` 가 한 번에 바꿉니다. 원장을 건드리는 일이라 조건을 셋 둡니다.

- **우리가 쓴 ISO 형식에 정확히 맞는 글자만** 건드립니다(`ISO_TEXT`).
  운영진이 손으로 적은 값은 그대로 둡니다 — `2026-09-19` 처럼 **파싱은 되지만
  우리 형식이 아닌** 것도 손대지 않습니다. "날짜처럼 보이면 다 바꾼다" 로 만들면
  의도하지 않은 칸까지 型이 바뀝니다.
- **가리키는 시점은 똑같습니다.** 표기만 바뀝니다.
- **여러 번 돌려도 같습니다** — 이미 Date 인 칸은 건너뜁니다.

메뉴 `시각 표기 통일` 이 서식 적용과 이 변환을 **함께** 합니다. 둘을 따로 두면
한쪽만 눌러 놓고 왜 안 바뀌는지 찾게 됩니다.

### 앱 화면은 바꾸지 않았다

이미 일관돼 있습니다 — 같은 날 안의 시각은 `UI.hhmm`(`14:05`), 일지처럼 날짜가
필요한 곳은 `UI.prettyDateTime`(`10월 31일 14:05`). 화면에 ISO 가 새어 나오는 곳은
없었습니다. 문제는 시트였습니다.

## D-041. 진행 사본 정합 — 넣고 나서 지운다 (DB 2단계 · 단계 C)

단계 B(D-038)의 upsert 는 **지우지 못합니다.** 시트에서 사라진 행이 DB 에 남습니다.
알고 미뤄 뒀던 숙제이고, 그래서 C 는 선택이 아니라 필수였습니다.

### 🔴 순서가 전부다

```
① 시트 전량을 `updated_at = 지금` 으로 upsert
② `updated_at < 지금` 인 행을 지운다   ← 시트에 없는 행만 남아 있다
```

**먼저 지우고 넣으면** 그 사이에 읽는 사람에게 **빈 표**가 갑니다. 이 순서면 표가
한순간도 비지 않습니다. "차이를 계산해서 지울 것만 고른다" 같은 것도 필요 없습니다 —
스탬프 하나가 그 일을 대신합니다.

**넣기가 실패하면 지우지 않습니다.** 실패한 채로 ②를 돌리면 표가 통째로 비어 버립니다.
이 두 가지를 테스트가 직접 검사합니다 — 순서를 뒤집으면 깨집니다(확인함).

### 조건 없는 DELETE 는 보내지 않는다

`supabaseDelete_` 는 `query` 가 비면 아무것도 하지 않습니다. PostgREST 에서 조건 없는
DELETE 는 표를 통째로 비우는 것이라, **실수 한 번이 사본 전체를 날립니다.**

### 트리거는 하나로 둔다

`mirrorDaily` 가 공개 데이터 푸시 · 진행 정합 · 정지 방지 ping 을 **한 번에** 합니다.
같은 일을 하는 트리거가 둘이면 하나는 반드시 낡습니다(D-032 의 판단 그대로).

**핸들러 이름을 `mirrorDaily` 로 유지한 이유**는 운영진이 **이미 그 이름으로 트리거를
걸어 뒀기 때문**입니다. 이름을 바꾸면 그 트리거가 조용히 죽습니다.

### 🔴 캠프 모드 — 10분 동기화는 그날만

평소에는 하루 1회로 충분합니다. 공개 데이터는 캠프 전에 확정되고, 진행 사본은 쓸
때마다 즉시 밀립니다(단계 B). 변경이 없어도 계속 도는 것은 낭비입니다(D-017).

캠프 당일만 다릅니다 — 운영진이 **시트에서 진행을 직접 고치는** 일이 생기고, 그건
앱을 거치지 않으므로 **주기 동기화만이 사본에 옮깁니다.**

그래서 메뉴에 `캠프 모드 켜기(10분)` 와 **`캠프 모드 끄기`** 를 같이 뒀습니다.
켜는 것만 있고 끄는 것이 없으면 반드시 켜 둔 채로 잊습니다.

### `progress_meta` — 단계 D 를 위한 신선도 근거

동기화할 때마다 `app_cache` 에 `progress_meta = { syncedAt, rows }` 를 남깁니다.

🔴 **신선도는 행이 아니라 동기화 시각으로 판단합니다.** 아무도 안 건드린 지점은
`updated_at` 이 원래 오래됐으므로, 행으로 판단하면 멀쩡한 값을 계속 버립니다.
단계 D 는 이 값을 봅니다.

### 사본 비용은 실측했다 — 요청 경로에서 뺄 이유가 없었다

설계 단계에서 "사본 쓰기가 무거우면 요청 경로 밖으로 빼야 하나" 를 고민했는데,
스크립트 속성을 꺼서 A/B 로 쟀습니다.

| `progress.set` 서버 시간 | |
|---|---|
| 사본 켜짐 | 6,002ms |
| 사본 꺼짐 | 5,120ms |
| **사본 비용** | **882ms** |

뺄셈으로 "3초쯤" 이라 추정했던 것이 틀렸습니다. 나머지 ~5초는 시트 읽기·쓰기입니다
(같은 측정에서 `progress.list` 서버가 1,336ms). **그래서 C 는 계획대로 정합과 지우기만
맡습니다.** 추측으로 구조를 바꾸지 않았습니다.

## D-042. 진행을 미러에서 읽는다 (DB 2단계 · 단계 D — 마지막)

조장이 캠프 당일 가장 자주 여는 화면입니다. 실측에서 GAS 로는
**2,442~3,807ms**(서버 1,336~2,519ms) 걸렸고, 같은 4G 에서 Supabase 직행은
**630~900ms** 였습니다.

`API.progressList(team)` 에 조 정보를 주면 **미러 → GAS** 순으로 갑니다.
안 주면 예전 그대로입니다.

### 🔴 계획을 바꾼 것 — 신선도는 `progress_meta` 가 아니라 **행 자신**으로 본다

설계 때는 "동기화 시각(`progress_meta`)을 따로 읽어 15분 기준으로 판단한다" 였는데,
만들면서 두 가지가 드러났습니다.

1. **요청이 하나 더 는다.** 두 번 왕복하면 2.4초가 되어 이득이 사라집니다.
2. **15분 기준은 평소에 작동하지 않습니다.** `progress_meta` 는 동기화 때만
   갱신되는데 평소 주기는 하루 1회입니다. 그러면 미러는 **항상** 버려지고
   D 는 캠프 모드에서만 의미가 있게 됩니다.

단계 C 를 만들고 나니 더 나은 답이 있었습니다 — **주기 동기화가 모든 행을 다시
씁니다.** 그래서 **가장 새로운 행의 `updated_at` 이 곧 동기화의 심박**입니다.
요청 하나로 데이터와 신선도를 같이 받습니다. (설계 때 "아무도 안 건드린 지점은
`updated_at` 이 원래 오래됐다" 고 적었는데, C 가 그 전제를 없앴습니다.)

기준은 bootstrap 과 같은 26시간입니다. 캠프 모드(10분)면 실제 지연은 10분 이내입니다.

### 🔴 내가 방금 쓴 것보다 낡으면 쓰지 않는다

가장 위험한 경우는 **사본 푸시가 실패한 뒤 읽는 것**입니다. 시트에는 새 값이,
사본에는 옛 값이 있습니다. 그대로 쓰면 **조장이 자기가 누른 값이 되돌아간 것처럼**
봅니다. 그래서 `progress.set` 성공 시각을 들고 있다가, 사본의 가장 새로운 행이
그보다 낡으면 GAS 로 갑니다. 푸시가 성공했다면 사본이 더 새로우므로 그냥 통과합니다.

### 🔴 빈 결과는 쓰지 않는다

아직 한 곳도 기록 안 한 조일 수도 있지만, **`anon` GRANT 가 없을 때도 똑같이 빈
배열**이 옵니다. 둘을 구분할 방법이 없으니 안전한 쪽으로 갑니다 — GAS 가 답합니다.
첫 기록 전 한 번만 손해입니다.

### 표에 없는 지점은 '대기' — 두 경로가 같은 화면을 그려야 한다

사본에는 **기록이 있는 지점만** 들어 있는데, 화면은 조의 코스 전체를 순서대로
보여 줘야 합니다. 그래서 `me.team.route` 를 기준으로 채웁니다.

이건 서버 `progressList_` 의 로직을 앱에 한 번 더 쓴 것이라 **어긋날 수 있는
지점**입니다. 브라우저 테스트가 미러 경로와 GAS 경로의 화면을 **문자열로 맞대 봅니다.**

### 설정 키가 빠지면 가드가 조용히 사라진다

`age > CFG.MIRROR_PROGRESS_MAX_AGE` 는 키가 없으면 `age > undefined` = false 라
**가드가 통째로 사라집니다.** 테스트를 만들다 실제로 이 상태를 밟았습니다.
없으면 `MIRROR_MAX_AGE` 로 넘어지게 했습니다 — 안전한 쪽입니다.

### 되돌리는 법

`config.js` 의 `SUPABASE_URL` 을 비우면 미러가 통째로 꺼지고 전부 GAS 로 갑니다.
`perf` 에 `progress.list:supabase` 와 `progress.list` 가 따로 남으므로, 사전답사에서
두 경로의 중앙값을 나란히 볼 수 있습니다.

## D-043. 진행 기록이 왜 8.5초인지 — **재고 나서 고친다**

단계 D 를 넣은 뒤의 실측입니다.

| 액션 | 클라이언트 | 서버 |
|---|---|---|
| `progress.list:supabase` | **62ms** | — |
| `fee.status` | 1,778ms | 613ms |
| `journal.list` | 2,304ms | 1,064ms |
| `auth.login` | 3,009ms | 1,611ms |
| **`progress.set`** | **9,836ms** | **8,502ms** |

읽기는 해결됐습니다 — `progress.list` 가 2,442~3,807ms 에서 **62ms** 가 됐습니다.

### 🔴 쓰기는 오히려 느려졌다

| 시점 | `progress.set` 서버 |
|---|---|
| 사본 꺼짐 (A/B, D-041) | 5,120ms |
| 사본 켜짐 | 6,002ms |
| 지금 | **8,502ms** |

사본 비용은 A/B 로 **882ms** 임을 확인했으니 그것으로는 설명이 안 됩니다.
그 사이에 들어간 것은 점수·메모 조건부 쓰기(D-039), 시트에 Date 쓰기(D-040),
주기 동기화(D-041 — `progress.set` 경로에는 없음)뿐인데 어느 것도 2.5초짜리가 아닙니다.

**그래서 아직 원인을 모릅니다.**

### 추측으로 고치지 않는다

이 세션에서 두 번 틀렸습니다. `withLock_` 락 타임아웃 가설은 실행 로그가 배제했고,
사본 비용 "3초쯤" 추정은 A/B 가 882ms 로 뒤집었습니다. **뺄셈과 추론으로는 계속
틀렸고, 실제로 잰 것만 맞았습니다.**

그래서 `progressSet_` 안을 구간별로 잽니다.

```
lock=…   락을 잡기까지 (경합이면 여기가 크다)
read=…   Progress 탭 전체 읽기
write=…  행 갱신·추가
list=…   progressList_ (Participants·Courses 를 더 읽는다)
mirror=… Supabase 사본 푸시
total=…  위 전체
```

### 어디에 남기나 — 이미 있는 자리에

`Log` 탭의 **`상세`** 칸에 한 줄로 남깁니다. 새 화면도, 새 통신 형식도, 새 표도
만들지 않습니다. 운영진이 시트에서 바로 읽고, 필요하면 그대로 복사해 보냅니다.

응답의 `ms`(D-035)에서 `total` 을 빼면 **나머지**(토큰 검증·명단 읽기·직렬화)도
나옵니다. 두 수로 전체가 갈립니다.

### 곁들여 — 로그를 락 밖으로 뺐다

`logEvent_` 도 시트 쓰기입니다. 락 안에 두면 다른 조장이 그만큼 더 기다립니다.
D-038 에서 사본 푸시를 락 밖으로 뺀 것과 같은 이유입니다. 덤으로 로그에
`mirror` 시간까지 담을 수 있게 됐습니다.

## D-044. 쓰기 8.5초의 범인은 **락 대기**였다 — 목록 만들기를 락 밖으로

D-043 의 계측이 답을 줬습니다. `Log` 탭의 `상세` 칸(연타한 5건):

```
lock=126  read=256 write=97  list=1061 mirror=1489 total=3099
lock=1464 read=427 write=578 list=907  mirror=1066 total=4582
lock=2978 read=456 write=155 list=951  mirror=942  total=5615
lock=4541 read=451 write=238 list=801  mirror=1076 total=7210
lock=4719 read=847 write=97  list=860  mirror=677  total=7264
```

### 🔴 제 예상이 또 틀렸다 — 혼자 눌러도 경합이 난다

D-043 에 **"`lock` 이 크면 실행 경합. 지금은 혼자 쓰시니 가능성이 낮습니다"** 라고
적었습니다. 틀렸습니다. **`lock` 이 126 → 1,464 → 2,978 → 4,541ms 로 쌓입니다.**

한 사람이 빠르게 누르는 것만으로 충분합니다. 각 요청이 락을 쥔 시간만큼 다음
요청이 줄을 서고, 연타하면 그게 누적됩니다. 캠프 당일 조장 9명이면 훨씬 나빠집니다.

이 세션에서 세 번째로 추측이 틀렸습니다(락 타임아웃 가설, 사본 "3초" 추정, 이번).
**잰 것만 맞았습니다.**

### 고친 것 — 락은 한 행의 읽고-고치고-쓰기만 잡는다

`progressList_` 가 **락을 쥔 채** 0.5~1.1초를 썼습니다. 그건 그냥 읽기라 락이
지켜야 할 것이 아닙니다. 락 밖으로 뺐습니다.

| | 락 보유 |
|---|---|
| 전 | read + write + **list** ≈ 0.8~2.5초 |
| 후 | read + write ≈ **0.3~1.4초** |

**락 보유 시간이 곧 다음 사람의 대기**이므로, 절반으로 줄면 대기도 절반으로 줍니다.
`mirror`(0.45~1.5초)는 D-038 에서 이미 락 밖이라 대기에 기여하지 않았습니다.

이건 주석으로 두면 되돌아갑니다. 하네스가 **락을 쥔 채 일어난 읽기**(`SHEET_OPS.lockedReads`)를
세고, 테스트가 "락 안에서는 Progress 만 읽는다" 를 검사합니다.
목록 만들기를 락 안으로 되돌리면 깨집니다(확인함).

### 🔴 명단 캐시는 넣었다가 되돌렸다

응답 `ms`(8,342)와 `total`(5,615)의 차이 **약 2.7초**를 `requireUser_` 의 명단
읽기로 보고 `CacheService` 캐시를 만들었습니다. **그런데 듣지 않습니다.**

`progressList_` 가 `teamMembers_`(`gas/Auth.gs:322`)로 **명단을 어차피 읽고**,
`readTable_` 은 실행 내 캐시가 있어 한 실행에서 명단은 어차피 한 번만 읽힙니다.
캐시가 그 한 번을 없애지 못합니다. **테스트가 이걸 잡아 줬습니다** —
"두 번째 요청은 명단을 읽지 않는다" 가 실패했습니다.

측정 없이 캐시를 넣는 것은 이 문서가 계속 피해 온 일이라 **되돌렸습니다.**
staleness 위험(조 배정이 바뀐 사람이 옛 조에 기록)을 이득 없이 지고 갈 이유가 없습니다.

### 대신 그 2.7초를 잰다

`requireUser_` 가 쓴 시간을 `auth=` 로 구간에 싣습니다. 다음 실측에서
**명단 읽기인지, 스프레드시트를 여는 고정 비용인지** 갈립니다. 후자라면 캐시로는
못 고치고 다른 수를 찾아야 합니다. 또 추측하지 않습니다.

## D-045. 진행 기록을 **묶어서** 보낸다 — Classfinder 의 batch 를 정동캠프에 맞게

D-044(목록 만들기를 락 밖으로)가 실물에서 들었습니다.

| | `progress.set` 서버 |
|---|---|
| 전 | 8,502ms |
| D-044 후 | **3,917ms** |

그래도 요청 수는 그대로입니다 — **지점 하나 누를 때마다 한 요청**입니다.

### 운영진이 답을 알고 있었다

Classfinder 의 흐름에 답이 있었습니다.

```
POST { session, batch:[{name,phone,status}] }
                 ↑ 배열
```

관리자가 여러 명을 찍고 **[저장]** 한 번 → 한 요청, 락 한 번.

### 🔴 그대로는 못 옮긴다 — UX 가 다르다

Classfinder 에는 [저장] 버튼이 있습니다. 정동캠프는 **지점 버튼을 누르는 것이 곧
저장**입니다. 저장 버튼을 새로 두면 현장에서 조장이 **저장을 잊고** 기록이 날아갑니다.

→ 배치를 **자동으로** 합니다. 낙관적 UI(D-037)가 이미 있어 화면은 즉시 바뀌므로
**전송만** 묶으면 되고, 사용자는 아무 차이를 못 느낍니다.

### 🔴 고정 디바운스가 아니라 "앞 요청이 도는 동안 모으기"

```
탭 ①   → 대기 중인 요청 없음 → 즉시 전송      (지연 0 — 빠른 길 유지)
탭 ②③④ → ①이 도는 중 → 큐에 쌓임
① 응답 → ②③④ 를 **한 요청**으로
```

800ms 같은 고정 디바운스는 **한가할 때 공연히 느려지고 바쁠 때는 여전히 모자랍니다.**
이 방식은 한가하면 0ms, 느리면 최대한 묶는 것을 알아서 합니다 — 왕복 3초 동안 탭이
쌓이는 지금 문제에 정확히 맞습니다.

큐는 **지점코드로 키를 잡은 map** 이라 같은 지점을 두 번 누르면 마지막만 남습니다.
서버도 같은 규칙입니다.

### 🔴 되돌릴 곳은 화면 스냅샷이 아니라 **마지막 서버 응답**

처음에는 배치 직전의 화면을 찍어 두고 실패 시 복원했습니다. **테스트가 잡았습니다** —
그 스냅샷에 앞 배치의 `저장 중` 표시가 남아 있으면 되돌릴 때 그것까지 복원돼
**영영 안 지워집니다.** 서버가 준 목록은 언제나 깨끗하므로 그걸 기준으로 삼습니다.

### 🔴 한 건이라도 잘못되면 전체를 거절한다

**전부 먼저 검증하고** 그다음에 씁니다. 쓰기 중간에 던지면 일부만 들어간 채로 끝나고,
화면과 시트가 어긋난 것을 되돌릴 방법이 없습니다.

### 🔴 번호는 이미 읽은 행에서 구한다

`nextId_` 는 시트를 **다시 읽고**, `appendRow_` 가 캐시를 비웁니다. 루프 안에서 부르면
새 행마다 **락을 쥔 채** 전량 재읽기가 생겨 D-044 가 한 일을 도로 무릅니다.
`maxIdNumber_(rows, …)` 가 이미 읽어 둔 행에서 최대값을 주므로, 한 번 구하고
지역에서 증가시킵니다. 테스트가 "락 안에서는 Progress 만 읽는다" 로 지킵니다.

### 앱이 닫힐 때

큐가 남은 채 탭이 가려지면 기록이 날아갑니다. `visibilitychange` 에서 즉시 보냅니다.

### 옛 앱 호환

서버는 단건 `{checkpoint, status}` 도 그대로 받습니다. 앱이 먼저 올라가든 GAS 가
먼저 올라가든 깨지지 않습니다.

## D-046. 운영 편의 네 가지와 **반려 재제출 버그** 하나

사전답사(09/30)를 앞두고 운영진이 쓰면서 나온 요청 다섯 건입니다. 넷은 개선이고,
하나는 **실제 버그**였습니다. 읽다가 찾았습니다.

### 🔴 반려된 일지는 고쳐도 다시 검수되지 않았다 (버그)

`journalUpdate_` 는 검수를 거친 글을 고치면 `대기` 로 되돌립니다. 그런데 조건이
**`승인` 뿐**이었습니다.

```js
if (… && str_(row['상태']) === '승인') { patch['상태'] = '대기'; }
```

원래 의도는 "승인 후 내용을 갈아 검수를 우회하는 길을 막는다" 하나였습니다.
그 결과 **반려된 글은 고쳐도 계속 `반려`** 였습니다 — 검수대기 목록에 다시 오르지
않으니 운영진은 고친 줄을 몰랐고, 참가자에게는 다시 낼 방법이 아예 없었습니다.

앱 쪽은 이미 준비돼 있었습니다. 반려 사유를 보여 주고 수정 버튼도 띄웁니다
(`item.canEdit`). **서버만 막고 있었습니다.**

→ `승인` **또는 `반려`** 면 `대기` 로 되돌립니다. **옛 반려 사유도 함께 지웁니다** —
안 그러면 새로 낸 글에 지난 사유가 붙어 있어, 고쳤는데도 반려된 글처럼 보입니다.

검수를 꺼 둔 상태(`JOURNAL_REQUIRE_APPROVAL=FALSE`)와 관리자 수정은 예전 그대로
상태를 건드리지 않습니다.

### 운영콘솔에서 **전체 일지**를 본다

`journalPending_` 은 `상태 === '대기'` 만 돌려줍니다. 그래서 승인·반려된 글은
운영콘솔에서 **아예 볼 수 없었고**, 잘못 올라간 사진을 뒤늦게 지울 방법이 없었습니다.

새 액션 **`admin.journal.list`** 는 삭제만 빼고 전부 최신순으로 줍니다
(`serializeJournal_` 재사용). 상태 거르기는 **앱이** 합니다 — 한 번 받아 두고 필터는
그 데이터로 돕니다. 145명 규모에서 전체 목록은 무겁지 않습니다.

카드 버튼은 **상태에 따라** 답니다. 승인된 글에 '승인' 버튼을 또 두지 않습니다.
기본 필터는 `검수 대기` 입니다 — 지금 하던 일이 그대로 되게.

### 🔴 가져오기와 그리기를 나눈다

필터를 누를 때마다 GAS 를 왕복하고 있었습니다. 원인은 한 줄이었습니다.

```js
bindSessionFilter(renderProgress);   // ← renderProgress 는 fetch + 그리기다
```

| | 하는 일 | 누가 부르나 |
|---|---|---|
| `renderX` | 캐시에 없으면 **가져와서** 담고 → `paintX` | 탭 진입 |
| `paintX` | 캐시로 **그리기만** | 필터 변경 |

캐시는 `state.cache = { review, progress, fee }` 한 곳입니다. **버리는 곳은 딱 둘**입니다.

- **탭 이동** — 운영진이 "다시 보려고 탭을 눌렀는데 옛 값" 이 되면 안 됩니다.
- **쓰기 성공 직후** — 승인·반려·삭제·설정 변경. 상태가 바뀌었는데 옛 목록을 그리면
  **화면이 거짓말합니다.**

시간 기반 만료(TTL)는 두지 않았습니다. 언제 낡는지는 시계가 아니라 **행동**이 압니다.

### 로그인에 이름·뒷 4자리를 기억한다

토큰 TTL 이 12시간이라 **캠프 당일 아침 조장 9명이 전부 다시 로그인**합니다.
`localStorage` 에 담아 두고 폼을 채웁니다. 성공한 값만 기억합니다.

🔴 **뒷 4자리는 사실상 비밀번호**입니다. 개인 폰을 전제로 저장하되,
**로그아웃하면 지웁니다** — 로그아웃은 "이 기기를 남에게 넘긴다" 는 신호로 봅니다.
토큰 만료로 다시 로그인하는 경우에는 그대로 남습니다. 그게 이 기능의 목적입니다.

체크박스는 달지 않았습니다. 공용 기기를 쓰게 되면 그때 답니다.

### 검증

GAS 20건 + 브라우저 12건을 더해 **680건**입니다. 전부 되돌려서 무는 것을 확인했습니다 —
조건을 `승인` 하나로 되돌리면 4건, 캐시를 빼면 1건, 탭 무효화를 빼면 1건,
`rememberLogin`/`forgetLogin` 을 빼면 각각 3건·2건이 깨집니다.

데모 가짜 백엔드에 `window.__DEMO_CALLS` 를 두어 **요청 수를 세서** 확인합니다.
"다시 부르지 않는다" 는 화면만 봐서는 증명되지 않습니다.

### 아티팩트 데모가 3주를 뒤처져 있었다

운영진에게 보내는 데모 링크(아티팩트)가 **2026-09-01 에 올린 것 그대로**였습니다.
그 사이 `docs/demo.html` 은 **18번** 다시 만들어졌습니다(`+1,143 / −181`).

원인은 코드가 아니라 **기록의 부재**입니다. 저장소 어디에도 그 주소가 없었습니다 —
`README.md`·`DEPLOY.md` 는 `node tools/build-demo.js` 를 돌리라고만 하고, 그 결과가
아티팩트로도 올라가 있다는 사실을 아무 데도 적어 두지 않았습니다. **적지 않은 절차는
돌지 않습니다.** 다시 올리는 것만으로는 또 어긋날 것이므로, 주소를 두 문서에 박았습니다.

자동화는 하지 않았습니다. 아티팩트 게시는 승인이 필요해 CI 로 걸 수 없고, 이 규모에서는
머지 체크리스트 한 줄이 맞는 답입니다.

🔴 **다시 올려도 이미 링크를 받은 사람은 옛 화면을 봅니다.** 공유 버전은 게시와 따로
움직여서, 아티팩트 화면의 공유 메뉴에서 옮겨 줘야 합니다.

## D-047. 설정을 바꾸면 **사본도** 민다 — 캐시가 세 겹이었다

사전답사 일정표를 시트에 다 넣었는데 앱에 뜨지 않았습니다. 시트는 멀쩡했습니다 —
재현해서 `bootstrap` 을 찍어 보니 17줄이 그대로 내려가고 있었습니다.

문제는 **앱이 그걸 안 본다**는 것이었습니다.

### 캐시가 세 겹이고, 서로 다른 것이 비운다

| 층 | 무엇이 비우나 | 안 비우면 |
|---|---|---|
| GAS 스크립트 캐시 | `clearConfigCache()` · 메뉴 · `onEdit` | 최대 5분 |
| **Supabase 사본** | **`mirrorPush()` 뿐** | **최대 26시간** |
| 브라우저 `sessionStorage` | 탭을 닫아야 (TTL 5분) | 탭이 살아 있는 동안 |

앱은 bootstrap 을 **미러 → GAS** 순으로 읽습니다(D-042). 그래서 **시트 쪽 캐시만 비우면
아무 소용이 없습니다** — 미러가 26시간 안이면 앱은 GAS 를 아예 부르지 않습니다.

### 🔴 사본을 미는 길이 하나 빠져 있었다

손으로 시트를 고치면 `onEdit` 이 밀어 줍니다(D-032). 그런데 **스크립트가 쓴 것은
`onEdit` 이 안 걸립니다** — 구글시트의 단순 트리거는 스크립트가 만든 변경에 반응하지
않습니다. `addSession` 이 일정표를 복사할 때 쓰는 `writeTimeline_` 이 정확히 그 경우였고,
그래서 사본은 **한 번도** 갱신되지 않았습니다.

같은 구멍이 세 군데였습니다.

- `admin.config.set` — **이게 제일 큽니다.** 운영콘솔에서 일지 작성을 닫아도 참가자
  화면에는 작성 폼이 그대로 있고, 올려야 그제서야 `CLOSED` 가 뜹니다. 서버는 제대로
  막고 있으니 구멍은 아니지만, 운영진은 껐다고 믿습니다.
- `회차 추가` 메뉴
- `일정 변경` 메뉴 — 사전답사가 끝나고 `SESSION_3_ACTIVE` 를 끌 때 같은 일이 납니다.

### 미는 자리는 **락 밖**, 묶음은 **한 번만**

`configSet_` 는 `withLock_` 안에서 돕니다. 거기에 네트워크를 넣으면 스크립트 전체가
그만큼 직렬화됩니다(D-044). 그래서 락이 풀린 뒤에 밉니다.

`changeSchedule` 은 `configSet_` 를 네 번 부릅니다. `withLock_` 에 중첩 가드가 없어
**안쪽 호출이 바깥 락 안에서 돕니다.** 각자 밀게 두면 측정상 **7번**이 나갔고 그게 전부
락 안이었습니다. `withoutMirrorPush_` 로 묶는 동안 멈추고 끝나서 한 번만 밉니다.

`mirrorPush` 는 이제 맨 앞에서 `mirrorEnabled_()` 를 봅니다. 어차피 못 보낼 값을 만드는 데
`bootstrap_()` 의 탭 읽기를 쓰지 않습니다.

### 새로고침은 세 번째 층을 못 지운다

`Ctrl+Shift+R` 은 HTTP 캐시를 비웁니다. `sessionStorage` 는 캐시가 아니라 **저장소**라
탭이 죽어야 사라집니다. 실제 브라우저로 재 보니 새로고침 두 번에도 `bootstrap` 호출은
**1번**에 머물렀고, `sessionStorage.clear()` 뒤에야 2번이 됐습니다. 시크릿 모드에서만
보였던 이유입니다.

TTL 5분은 그대로 둡니다 — 캠프 당일 참가자 폰이 페이지를 다시 열 때 즉시 뜨는 값이
왕복 한 번보다 큽니다. 대신 **운영콘솔은 이미 `API.bootstrap(true)` 로 강제**하므로
운영진 화면은 이 문제가 없습니다.

## D-048. 공지를 운영콘솔에서 쓴다 — 그리고 리스너가 쌓이고 있었다

데모에는 홈에 공지 카드가 있는데 실제 앱에는 없다는 제보에서 시작했습니다.
고장이 아니었습니다 — **`Notices` 탭이 비어 있었습니다.**

- 초기 세팅은 `Notices` 의 **헤더만** 만듭니다. `seedNotices_` 자체가 없습니다.
- 데모의 공지 둘은 `tools/build-demo.js` 에 박아 둔 **가짜 데이터**입니다.
- 앱은 공지가 없으면 카드를 통째로 숨깁니다.

🔴 그리고 **운영콘솔에서는 공지를 쓸 수 없었습니다.** 콘솔이 만지는 것은 `Config` 의
`NOTICE_TICKER`(앱바 아래 한 줄 띠)뿐이고, 홈의 공지 카드는 `Notices` 탭에서 옵니다.
올리려면 시트를 열어야 했는데, 캠프 당일 운영진은 폰을 봅니다.

### 콘솔은 **전부** 봐야 한다

`activeNotices_` 는 지금 보이는 것만 줍니다. 예약된 것도 종료된 것도 보여야 고치고
지울 수 있으므로 `noticeAll_` 을 따로 뒀습니다 — `journalPending_` 과 `journalAll_` 의
관계 그대로입니다 (D-046). 상태(`게시중`/`예약`/`종료`)는 **서버가 정합니다.**
화면이 날짜를 다시 해석하면 둘이 어긋납니다.

고를 수 있는 대상(`targets`)도 응답에 싣습니다. 시트 드롭다운이 쓰는 것과 같은 목록이라,
앱이 부서 이름을 따로 갖고 있다가 낡는 일이 없습니다.

### 🔴 같은 실수를 새 코드에서 다시 했다

`noticeSave_` 에 `mirrorPush()` 는 넣었는데(D-047) **`clearConfigCache()` 를 빠뜨렸습니다.**
`bootstrap_` 은 300초 캐시라, **낡은 사본을 밀어 버렸습니다** — 공지를 올렸는데 사본에는
빈 목록이 실려 갔습니다.

테스트가 잡았습니다. 푸시 **횟수**만 셌다면 통과했을 겁니다. **실린 값**까지 본 덕분에
보였습니다. 사본 검사는 앞으로도 "밀었나" 가 아니라 "무엇을 밀었나" 를 봅니다.

### 🔴 다시 그릴 때마다 클릭 리스너가 쌓이고 있었다 (기존 버그)

공지 삭제 테스트가 모달을 **두 개** 띄우면서 드러났습니다.

`setView` 는 `#view` 의 `innerHTML` 만 갈아 끼웁니다. `#view` 자체는 살아남으므로
그릴 때마다 `addEventListener` 를 부르면 리스너가 그대로 쌓입니다.
**일지 검수에도 있던 버그입니다** — 상태 필터를 세 번 누르고 승인을 누르면
승인 요청이 **세 번** 나갔습니다. 화면상으로는 티가 안 납니다.

핸들러를 `setView` 가 소유하게 했습니다 — 새로 달기 전에 이전 것을 뗍니다.
회귀는 요청 **수**로 지킵니다. 눈으로는 안 보이는 종류의 버그입니다.

### 삭제는 행을 실제로 지운다

일지는 `상태=삭제` 로 남기지만(D-009) `Notices` 에는 `상태` 칸이 없고, 잘못 올린 공지가
흔적으로 남을 이유도 없습니다. 저장소 최초의 물리 삭제라 `deleteRow_` 를 새로 뒀습니다.

🔴 **행을 지우면 뒤 행 번호가 당겨집니다.** 캐시를 안 버리면 그다음 수정이 엉뚱한 행을
고칩니다. 테스트가 "삭제 뒤에도 옳은 행을 고친다" 로 지킵니다.
